# Pek.RCode 使用规范

> **所有使用 `pek-rcode` 的项目，开工前必须先读本规范。**
> 本规范把"容易踩的坑"固化为可勾选的条目；每一条都对应过实际事故或已量化的性能问题。
>
> 适用版本：0.1.0（2026-10-22 起）。相关章节：[README](../README.md)、[决策记录](决策记录.md)。

---

## 0. 一页速查（先看这个）

| 你要做的事 | 正确写法 | 禁止 |
|-----------|---------|------|
| 定义实体 | `rcodegen` 从 `Model.xml` 生成 | 手写实体字段并直接赋值（无脏追踪 → 全列写） |
| 改字段 | `set_xxx(v)` | `entity.xxx = v`（字段私有，改不了；若手写实体则静默丢更新） |
| 只读查询 | `dal.read_session()` / `dal.read_session_for("表名")` | 只用 `open_session()` 却抱怨主库压力大 |
| 写入 | `dal.open_session()` + `insert/update/delete` | 用 `read_session()` 取到的会话写（从库会报错） |
| 批量写 | `insert_batch` / `upsert_batch` / `save_batch`（5000/批） | 循环里逐条 `save` |
| 日志/流水表 | `Model.xml` 加 `InsertOnly="True"` | 日志表用 `save` 判存在性（多一次查询） |
| 必填字段校验 | 生成代码已带（覆写 `validate` 叠加业务规则） | 自行在业务层重复判空却漏了 `insert` 前的拦截 |
| 导入历史数据 | `save_without_valid` | 为了导入把必填校验从 `validate` 里删掉 |
| 并发写共享表的某列 | `update_if_unchanged`（旧值进 `WHERE`）/ `increment` | 读出来改再整行写（会覆盖） |
| 配置类小表缓存 | `EntityCache`（≤1000 行） | 给设备表/消息表开整表缓存 |
| 强一致的读 | `CacheConsistency::Blocking`（默认） | 需要强一致时开 SWR |
| 会话 | 每个线程 `checkout` 一个，用完归还 | 把 `session` 跨线程共享 |
| 实体 | 每条消息构造/装载后丢弃 | 常驻百万实体对象 |

## 1. 实体规范

### 1.1 必须用生成器

```bash
cargo run --bin rcodegen -- --model Entity/Model.xml --out src/entities
```

生成的实体具备：字段**私有**、`xxx()` / `set_xxx()` 访问器、`dirty_state()`、`column_value()`。

**为什么必须**：脏追踪依赖 `set_xxx` 登记脏列。手写实体默认 `dirty_state() == None`，
`update` 会写**全部非主键列**——宽表等于每行多写几十列，且并发下会把别人的修改覆盖回旧值。

### 1.2 只能通过 setter 改值

```rust
// ✅
order.set_amount(dec!(100));
// ❌ 手写实体里这样写，脏列表为空 → update 返回 0，数据静默不落库
order.amount = dec!(100);
```

### 1.3 不要跨线程共享同一个实体

`DirtyState` 内部是互斥锁；跨线程改同一实体会产生锁争用，且语义混乱。
每条消息/每个连接处理线程**自己拥有实体**。

## 2. 表配置规范（`Model.xml`）

| 属性 | 用途 | 注意 |
|------|------|------|
| `InsertOnly="True"` | **仅插入表**（日志/记录/事件） | 生成实体声明 `insert_only()=true`：`update`/`delete` 直接报错，`save`/`save_batch`/`enqueue_save` **不查存在性直接插入**（省一次查询/行） |
| `Migration="Off"│"ReadOnly"` | 表级结构迁移收紧 | 只能比全局更严；`ReadOnly` = 只生成 DDL 不执行。**不影响 CRUD 性能** |
| `MaxCacheCount="0"` | 禁用该表整表缓存 | 大表/写频繁表必须设 0 |
| `ConnName="X"` | 该表落指定连接（分库） | 需先 `shards::register_connection` |

> **澄清**：DH.NCode 没有"表只读（禁止写数据）"的配置。表级只读只有两条路——
> `InsertOnly`（只插不改不删）与 `Migration="ReadOnly"`（结构迁移只读）。
> 需要"整张表禁止写"请用**只读连接**（连接串 `Readonly=true`）。

**表配置改完必须跑**：`dal.sync_schema()`（建表/补列），并核对 `SchemaReport`。

## 3. 读写分离规范

### 3.1 配置

```toml
# Config/Database.toml
[connections.main]
connection = "Server=db-master;Database=demodb;Uid=app;Password=***;Provider=MySQL;Pooling=true"

# 约定与 C# 完全一致：主连接 X → X.readonly（单副本）或 X.readonly.rd0/rd1/…（多副本轮询）
[connections."main.readonly.rd0"]
connection = "Server=db-slave1;Database=demodb;Uid=app_ro;Password=***;Provider=MySQL;Readonly=true"

[connections."main.readonly.rd1"]
connection = "Server=db-slave2;Database=demodb;Uid=app_ro;Password=***;Provider=MySQL;Readonly=true"
```

```rust
// 启动时挂载（只读副本按轮询分配读流量）
let replicas = Dal::read_replicas_from_file(&file, base, "main")?;
dal.attach_read_replicas(replicas);

// 可选：这些表写入后立刻要读最新值 → 强制读主库
dal.set_ignore_tables(&["DH_Order", "DH_Stock"]);
```

### 3.2 用法

```rust
// ✅ 只读查询
let mut s = dal.read_session().unwrap();
let list = Order::query(&dal, s.as_mut(), &query)?;

// ✅ 需要按表判断（写法更保险：忽略表自动回主库）
let mut s = dal.read_session_for("DH_Order").unwrap();

// ✅ 写入
let mut s = dal.open_session().unwrap();
order.insert(&dal, s.as_mut())?;
```

**纪律**：

1. **事务里不要用 `read_session`**。本库的会话是显式取出的，`read_session` 返回的是独立会话、
   不在事务中；如果你的逻辑需要"同一事务内读写一致"，请全部使用 `open_session` 的那个会话。
2. **写只能走主库会话**。副本连接一律加 `Readonly=true`，误写会在**调用点立刻报错**，
   不会等到数据库拒绝（省一次往返，且错误信息明确）。
3. **主从延迟兜底**：`dal.set_primary_only(true)` 一键全切主库（对账/迁移/延迟告警时）。
4. **副本不可用自动回退主库**（可用性优先）；不要依赖副本"一定被用到"。

### 3.3 C# 对照

| C# / DH.NCode | 本库 |
|---|---|
| 连接名 `X.readonly` / `X.readonly.rdN` | 同（`Dal::read_replicas_from_file`） |
| `DAL.Reads` 轮询 | `Dal::read_session()` |
| `ReadWriteStrategy.IgnoreTables` | `Dal::set_ignore_tables` |
| `ReadWriteStrategy.IgnoreTimes` | **不提供**（时段判定依时区；改用 `set_primary_only`） |
| `DbBase.Readonly`、`SuspendReadOnly`/`ResumeReadOnly` | 连接串 `Readonly=true`、`Dal::set_readonly(bool)` |

## 4. 缓存规范

| 表类型 | 建议 |
|--------|------|
| 配置/字典/权限（≤1000 行，读多写极少） | **默认即生效**：`MaxCacheCount` 缺省 1000，生成的 `find_by_xxx` 自动走整表缓存 |
| 允许秒级旧值 | `set_consistency(StaleWhileRevalidate { max_stale: 5s })` ✅ |
| 设备表 / 消息表 / 日志表 / 万行以上 | `Model.xml` 设 `MaxCacheCount="0"`（时序/分表列会自动 0） |
| 单条按主键热点读 | `SingleCache` ✅ |
| 需要精确行数 | `SELECT COUNT(*)`（`Dal::cached_count` 是 60 秒近似值，只用于缓存阀值判定） |

**红线**：整表缓存 = 一次 `SELECT *` 全表进内存 + 写后失效导致下次读重载。
写频繁的表开整表缓存 = 每次读都在查全表。

### 4.1 小表自动缓存（`MaxCacheCount`）

- `rcodegen` 为每个**唯一索引**（列全部非空）生成 `find_by_xxx`，内部 `Entity::find_cached_by`：
  表行数 < `MaxCacheCount` → 整表缓存内存匹配（**零 SQL**）；否则走 SQL。
- 行数来自 `Dal::cached_count`（60 秒缓存、写入即失效；SQLite 用 `MAX(自增列)`）。
- **`DataScale="time"` / `timeShard` 的表自动禁用**（时序/分表不缓存）。
- 手写实体也可直接用：`Self::find_cached_by(dal, session, &[("Code", DbValue::Text(code))])`。

### 4.2 视图与仅插入表

| 表配置 | 行为 |
|--------|------|
| `<Table IsView="True">` | **禁一切写入**（报「视图无法添删改！」）+ 跳过结构迁移/分表建表 |
| `<Table InsertOnly="True">` | 禁 `update`/`delete`；`save`/`save_batch`/`enqueue_save` 不查存在性直接插入 |

### 4.3 数据校验（`Valid`，对齐 DH.NCode）

- `rcodegen` 为「**非空字符串列**（无默认值、非审计列）」生成 `validate`：
  空串/空白 → `Error::Validation("XX 不能为空")`。
- **调用点**：`insert` / `update` / `insert_sharded` 在**产生任何 SQL 之前**校验；
  失败直接返回错误，不写库。
- **无脏数据则跳过**（对齐 C# `if (!HasDirty) return true`）；
  手写实体没有脏追踪 → **始终校验**。
- **删除不校验**（对齐 C# `DataMethod.Delete` 分支）。
- **批量写入不逐条校验**（`insert_batch` / `save_batch` 保持批量语义），
  需要校验时循环调 `insert`，或在业务层先校验一遍。
- **导入历史数据**要跳过校验时用 `save_without_valid`（对齐 C# `SaveWithoutValid()`）。
- 业务自定义校验：覆写 `fn validate(&self) -> Result<()>`（可叠加长度/格式/枚举范围检查）。

```rust
impl Entity for Order {
    fn validate(&self) -> Result<()> {
        if self.code.trim().is_empty() {
            return Err(Error::Validation("单号 不能为空".into()));
        }
        if self.amount < rust_decimal::Decimal::ZERO {
            return Err(Error::Validation("金额不能为负".into()));
        }
        Ok(())
    }
}
```

> 审计列（`CreateUser`/`CreateTime`/`UpdateUser`/`UpdateTime`/`Remark`/`TraceId` 等）**不参与必填校验**，
> 与 C# `_validExcludes` 一致（这些列常由拦截器自动填充）。

### 4.4 原子累加（`AdditionalFields` 等价能力）

**计数器/流量/积分等「累加」字段，必须用累加 API，不要「读出来改再写回」**——
后者在并发下会丢更新（A、B 同时读到 100，各写 101，实际应是 102）。

```rust
// 表级（最常用）：一条语句完成 `Count = Count + ?`
table.increment_by_pk(session, &[DbValue::Int(id)], &[
    ("Count", DbValue::Int(1)),
    ("Flow", DbValue::Int(bytes)),
])?;

// 条件累加：一条语句给多行加同一个增量
table.increment(session, &[("Flow", DbValue::Int(5))], &Where::new().like("Name", "dev-%"))?;

// 实体级：累加后把新值同步回对象
stat.increment(dal, session, &[("Count", DbValue::Int(1))])?;
```

- 底层生成 `UPDATE t SET "Count" = "Count" + ? WHERE ...`，由数据库在单条语句内完成读-加-写；
- 累加列应在 `Model.xml` 里给 `DefaultValue="0"`（否则插入时必须显式写初值，NOT NULL 会拒绝）；
- 累加**不做数值类型校验**（由数据库报错），文本列累加会直接失败——这是预期行为；
- 写入后自动让相关缓存失效（与 `update` 一致）。

### 4.5 多系统共享表（多个应用写同一张表）

**根因不是缓存，而是 UPDATE 的 `SET` 里放了哪些列**：缓存只是让"旧值"有机会进入写路径；
即使完全没有缓存，两个系统各自「读整行 → 改一个字段 → 全列写」也会互相覆盖
（A 读 → B 读 → A 写全列 → B 写全列，A 的修改被整行抹掉）。

**写路径对照**（同一张表被多个系统同时写时，按此表选择方法）：

| 写路径 | `SET` 的列 | 共享表可用性 |
|--------|-----------|-------------|
| 生成实体 `update` / `save` / `update_batch` / `save_batch` / `update_sharded` | **仅脏列**（`set_xxx` 登记；无脏 → 返回 0、不发 SQL） | ✅ 首选 |
| `update_columns(dal, session, &["A","B"])` | 显式列集 | ✅ |
| `update_where(sets, filter)` | 显式列集（一条语句改多行） | ✅ |
| `increment` / `increment_by_pk` | `SET c = c + ?`（库内原子累加） | ✅ 计数/余额唯一正解 |
| `TableRef::upsert_by_key` | 只写传入的 `values` 列 | ✅ |
| `enqueue_save` | 行存在 → `upsert_tracked`，只写脏列 | ✅ |
| **手写实体 / `#[derive(Entity)]`** 的 `update`/`save`/`update_batch`/`save_batch` | **全部非主键列**（`dirty_state()` 默认 `None`） | ❌ 改用 `update_columns` / `update_where` |
| `upsert_batch` / `replace_batch` / `write_batch(Upsert\|Replace)` | **SQL 级整行覆盖** | ❌ 仅限导入/快照还原 |
| `TableRef::save(SaveModes::Upsert/Replace)` | 传入的 `fields` 全进 `SET`（传全字段即整行） | ⚠️ 只传需要写的列 |

**跨进程缓存事实**：`EntityCache` / `SingleCache` 的失效只在**本进程**发生（写库后调本进程的
`invalidate_cache`）；别的系统写库**不会通知本进程**，默认 60 秒内仍可能读到旧值。
因此**被多个系统写的表一律 `MaxCacheCount="0"`**，缓存只留给纯字典/只读小表。
另外 `save` 在**无自增列**时用 `Entity::find` 判存在性，开启 `SingleCache` 后可能读到旧值，出现
"误判不存在 → 插入冲突"或"误判存在 → update 0 行静默不落库"。

**"值没变就不写"（字段自己 = 字段自己）能做到什么、做不到什么**：

- 生成实体的 setter 已实现"值相同直接返回、不标脏" → 这类**不会产生 SQL**；
- 但它防的是"**没改**"，不防"**改了、但依据的是旧值**"——跨进程仍可能把别人刚写的同名列覆盖回去
  （列级 last-writer-wins）；
- "先改成 B 再改回 A" 仍会保留脏标记（`DirtyCollection` 能记旧值，但生成代码走 `mark_static`
  未填旧值），最终写一次原值：库内未变时无害，库内**已变时即覆盖**；
- **彻底的做法是条件更新（逐列 CAS / 乐观锁）**——把“我读到的旧值”放进 `WHERE`。
  库已内置两个原语（2026-10-23）：

```rust
// 表级：一条 UPDATE ... SET ... WHERE 主键 AND 期望列=旧值；返回 0 = 冲突
let affected = dal.table("Order")?.update_if(
    session.as_mut(),
    &[("Amount", new_amount)],     // SET：只写要改的列
    &[DbValue::Int(id)],           // 主键
    &[("Amount", old_amount)],     // 读取时的旧值（不是实体当前值）
)?;
if affected == 0 { /* 已被别的系统改过：重读合并 / 重试 */ }

// 实体级：自动只写脏列，冲突返回 Error::Conflict（脏数据保留，便于合并后重试）
match order.update_if_unchanged(&dal, session.as_mut(), &[("Amount", old_amount)]) {
    Ok(_) => {}
    Err(Error::Conflict(_)) => { /* 重读合并后再提交 */ }
    Err(e) => return Err(e),
}
```

  - 表级 `update_if`：`0` = 主键不存在或期望值已变；**冲突也会失效本进程缓存**
    （否则重试会一直命中旧值）。
  - 实体级 `update_if_unchanged`：无脏 → `Ok(0)` 不发 SQL；冲突 → `Error::Conflict` 且**不清脏**；成功后清脏。
  - 成本（实测 SQLite、事务内，2026-10-23 三轮优化后）：`update_if` ≈ **0.78 µs**/次 vs `update_by_pk` ≈ **0.73 µs**
    （+0.07 µs；数据库执行约 0.42 µs，框架侧约 0.31 µs）。
    只在共享表并发敏感字段上使用，普通表用 `update` 即可。
  - 边界：**分表不支持**（返回 `Error::Unsupported`）；`expected` 传读取时的旧值；空 `expected` 等价无保护。
  - 也可以用 `Version` 列：`SET Version = Version + 1` 且 `WHERE Version = 旧版本`。

**共享表 6 条**：
1. 只用生成实体 + setter；手写/`derive` 实体不要用 `update`/`save`。
2. `MaxCacheCount="0"`；不要对共享写表开整表缓存 / 单对象缓存。
3. 禁用 `upsert_batch` / `replace_batch`（整行覆盖语义）。
4. 计数/余额/库存用 `increment`，不要「读出来加一再写」。
5. 需要"有则改无则插"且只改少数列：用 `upsert_by_key`，不要用 `upsert_batch`。
6. 会并发写同一列的字段：用 `update_if_unchanged`（旧值进 `WHERE`）或 `Version` 列，
   `Error::Conflict` / `affected == 0` 视为冲突并重读合并。

## 5. 批量写入与队列规范

| 场景 | 用 |
|------|-----|
| 纯新增（日志/流水） | `insert_batch`（或 `InsertOnly` 表 + `save_batch`） |
| 按主键**整行**插入或覆盖 | `upsert_batch`（导入/快照还原用；**多系统共享表禁用**，见 §4.5） |
| 混合新增/更新 | `save_batch`（内部合并批插 + 逐条更新，更新只写脏列） |
| **多行改同一值**（批量改状态/打标） | `Entity::update_where(dal, session, &[("Status", v)], &Where::new().eq(..))` —— **1 条语句** |
| 多行改不同值 | `update_batch`（逐条，SQL 无通用多行 UPDATE） |
| 跨表/跨库分片 | `insert_batch_sharded` / `save_batch_sharded` |
| 有延迟需求、可批量落库 | `Entity::enqueue_save` + `EntityQueue::flush`（**flush 由你驱动**，库内无定时器） |

- 批大小默认 5000（对齐 C# `GetBatchSize()`），可传入更小值控制单条 SQL 体积；
- `enqueue_save` 会为每条记录构造完整字段集（非零拷贝）：超高吞吐优先用 `*_batch` 系列；
- **不要**在循环里 `save()` 单条——每次至少一次往返。

## 6. 会话、事务与线程规范

1. **一个线程一个会话**：从 `dal.open_session()` / `read_session()` 取，作用域结束自动归还池。
2. **不要跨线程传递会话**（`SqlSession: Send` 但池化会话有归属，跨线程使用会打乱池统计）；
   需要并行就各线程各取一个。
3. **事务范围要短**：`begin` → 少量写 → `commit`。长事务会长期持有行锁并放大主从延迟。
4. **连接池**：默认 `Min=CPU(2–8)`、`Max=1000`、空闲 30s 回收。
   并发写线程数远小于 1000 时应调小 `Max`，避免把数据库连接数打满
   （连接串 `MaxPoolSize=` 可调）。

## 7. 分表 / 分库规范

```rust
shards::register_connection("DH_2027", other_dal)?;      // 对齐 C# DAL.AddConnStr
let policy = TimeShardPolicy::new("CreateTime")
    .with_conn_policy("{0}_{1:yyyy}")
    .with_table_policy("{0}_{1:yyyyMMdd}");
log.insert_sharded(&dal, session.as_mut(), &policy)?;    // 自动路由 + 自动建表
```

- 未注册的连接名按 C# 规则自动落 `{程序目录}/Data/{连接名}.db`（可用 `shards::set_auto_db_dir` 改）；
- 分表**写操作自动建表**；`Migration=Off`/`ReadOnly` 档下不建（与 C# 一致）；
- 跨分片查询用 `query_sharded` / `count_sharded` / `delete_sharded`，不要手写 `UNION`。

## 8. 性能红线（本机实测，release）

| 操作 | 数量级 | 说明 |
|------|--------|------|
| 字段赋值（脏登记） | ~36 ns，**0 分配** | 生成实体 `mark_static` |
| 5 列保存周期（登记+取列+清空） | ~138 ns，**0 分配** | 禁止退回到 `names()` 全量转 String |
| 缓存命中（元数据） | ~13 ns | 原子读 + 一次读锁 |
| 缓存命中（8 线程并发） | ~50 ns/op | 争用已消除 |
| **会话借出+归还**（连接池） | ~152 ns；8 线程 **~194 ns** | 分片池，劣化 1.28×（可随核数扩展） |
| **读会话获取**（`read_session_for`） | ~167 ns，1 次分配 | 无副本/无忽略表时**零锁** |
| **按列名取值**（20 列宽表） | ~17 ns，**0 分配** | 列名索引原文命中 |
| **插入一行**（20 列，SQLite） | **~3.6 µs** | 2026-10-23 三轮优化后（原 9.0 µs，−60%） |
| **按主键更新**（事务内） | **~0.73 µs** | 数据库 ~0.42 µs + 框架侧 ~0.31 µs |
| **CAS 条件更新**（事务内） | **~0.78 µs** | 比普通更新 +0.07 µs；冲突路径 ~0.70 µs |
| **查询一行**（20 列，SQLite） | ~5.6 µs | 语句缓存后；其余是 SQLite 执行 |

**SQLite 连接参数**（默认对齐 C# DH.NCode：`Journal Mode=WAL` + `Synchronous=Off`）：
连接串可覆盖——`Synchronous=Normal|Full|Extra`、`Cache Size=-8192`（KiB，负数单位）、
`Journal Mode=WAL|Delete|...`、`BusyTimeout=5000`（毫秒）、`Readonly=true`（跳过 journal_mode）。
`Synchronous=Off` 最快，但**断电可能损坏数据库**；需要强一致的项目请显式设 `Synchronous=Normal`。
| 单条 `save` | 至少 1 次往返 + 1 次查询（非 InsertOnly 判定） | 高吞吐请用批量 |

回归基准：`cargo test --release --test perf_guard -- --ignored --nocapture --test-threads=1`

**改动以下代码后必须重跑基准**：`dirty.rs` / `cache.rs` / `session.rs`（`DbRow`/`RowSet`）/
`entity.rs` 的写路径 / `sqlite.rs`（语句缓存与参数绑定）/ `pool.rs`（连接池分片）。

### 8.1 百万级设备高并发（IoT / 海量连接场景）

**框架侧已保证**（实测数据见 `docs/审计报告-性能与资源-2026-10-22-第十一轮.md`）：
- 热路径**零线程新建**（连接池、语句缓存、缓存刷新都在调用方线程内完成）；
- **读路径零堆分配**（会话获取 1 次 `Box`、按列名取值 0 次、缓存命中 0 次）；
- 连接池按线程分片，8 线程吞吐劣化仅 **1.28×**（不再串行）。

**业务侧必须遵守的 5 条**（否则框架再快也没用）：
1. **每条消息短事务**：不要在一个事务里做网络/计算；事务长度直接决定行锁与 WAL 大小。
2. **实体即用即弃**：处理完消息立刻丢弃实体，**不要**为百万设备各建一个常驻实体对象
   （每实体 32 字节脏状态 + 字段 String）。
3. **批量优先**：日志/上报/心跳一律 `insert_batch`（5000/批）；单条 `save` 至少 2 次数据库交互。
4. **不要在 100 万行的表上开整表缓存**：`MaxCacheCount` 只给 ≤1000 行的配置/字典表。
5. **连接池 `Max` 按数据库能力设**：默认 1000 是「空闲上限」，不是并发上限；
   MySQL 的 `max_connections` 通常远小于它 —— 用连接串 `MaxPoolSize=` 调小，否则会把数据库打满。

## 9. 常见错误对照表

| 现象 | 根因 | 正解 |
|------|------|------|
| `update` 返回 0，数据库没变化 | 手写实体直接改字段，脏列表为空 | 用 setter；或改用生成实体 |
| 更新把别的线程刚写的列覆盖回旧值 | 未启用脏追踪，写全列 | 用生成实体（只写脏列） |
| 跨系统共享表：别的系统改的列被覆盖回旧值 | 手写实体全列更新，或用了 `upsert_batch`/`replace_batch` | 生成实体 + 脏列；共享表禁用整行覆盖（§4.5） |
| 共享表读到 60 秒前的旧值 | 表被别的进程写，本进程缓存收不到通知 | 共享写表 `MaxCacheCount="0"`（§4.5） |
| 条件更新返回 0 / `Error::Conflict` | 期望列已被别的系统改过（或主键不存在） | 重读合并后用新值重试；不要当成功处理 |
| 日志表插入很慢 | 每行都 `save`（判存在性） | `InsertOnly="True"` + `insert_batch` |
| 内存暴涨 | 给大表开了整表缓存 | `MaxCacheCount=0`，改按主键查 |
| 主库 CPU 高、从库闲置 | 读也走 `open_session` | 读用 `read_session_for("表名")` |
| 从库报"read-only"错误 | 用副本会话执行写 | 写用 `open_session`；副本连接加 `Readonly=true` 提早暴露 |
| 读到刚写入的数据却是旧值 | 走的是副本（主从延迟） | 该表加入 `set_ignore_tables` 或临时 `set_primary_only(true)` |
| 启动时报"表已存在" | 并发首开未单飞 | 用 `pek_rcode::store::SharedStore`（库内已单飞） |
| 分表查询缺数据 | 跨分片只查了一张表 | 用 `query_sharded` |
| 生产被自动删列 | `Migration=Full` | 生产用 `On`（只建不改不删） |

## 10. 接入检查清单（每个新项目/新表过一遍）

- [ ] 实体由 `rcodegen` 生成，字段私有，改值走 `set_xxx`
- [ ] 所有写路径在事务/会话作用域内，会话未跨线程
- [ ] 读多写少的查询使用 `read_session`（或 `read_session_for`）
- [ ] 日志/流水/事件表配置 `InsertOnly="True"`，批量写入
- [ ] 必填列在 `Model.xml` 里保持 `Nullable="False"` 且无 `DefaultValue`（才会生成 `validate` 校验）；
      业务规则覆写 `validate` 叠加；导入场景用 `save_without_valid`
- [ ] 整表缓存仅用于 ≤1000 行的配置类表；大表 `MaxCacheCount=0`
- [ ] 被多个应用同时写的表：`MaxCacheCount="0"`，写路径只用脏列/显式列集，
      未使用 `upsert_batch`/`replace_batch`；并发列有 `Version` 或条件更新（§4.5）
- [ ] 强一致场景使用默认 `Blocking`，未误开 SWR
- [ ] 分表/分库通过 `TimeShardPolicy` + `register_connection`，无手写跨库 SQL
- [ ] 生产连接串 `Migration` 为 `On`（或更严），副本连接 `Readonly=true`
- [ ] 批量路径使用 `*_batch`，批大小 ≤5000
- [ ] 改动写路径后跑过 `perf_guard` 基准与全量测试
