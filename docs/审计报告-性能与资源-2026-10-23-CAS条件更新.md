# 审计报告：条件更新（CAS）原语 · 性能与资源

> 日期：2026-10-23
> 范围：`TableRef::update_if`、`Entity::update_if_unchanged`、`Error::Conflict`（本轮新增）
> 背景：多应用/多系统共享同一张表时，普通 `update` 仍可能把「读到的旧值」覆盖到别人刚写入的行上
> （列级 last-writer-wins）。上一轮已在 `docs/使用规范.md` §4.5 给出 `update_where` 的 CAS 写法，
> 本轮把它固化为库内原语，并按用户要求做性能与资源审计。

---

## 一、设计结论

| 项 | 结论 |
|----|------|
| 语义 | `UPDATE ... SET sets WHERE 主键 AND expected 列 = 旧值`，一条语句完成"检查 + 更新" |
| 表级返回 | `u64` 受影响行数：`1` = 成功；`0` = 主键不存在或期望值已变（冲突） |
| 实体级返回 | 成功 `Ok(affected)`；冲突 `Err(Error::Conflict)`；无脏 `Ok(0)`（不发 SQL） |
| 冲突时脏数据 | **保留**（便于重读合并后再次提交）；成功后清空 |
| 冲突时缓存 | **失效本进程缓存**——否则重试会一直命中旧值、永远冲突（正确性要求） |
| 分表 | 不支持（返回 `Error::Unsupported`；分表场景请用具体分表句柄或 `increment`） |
| 视图 / InsertOnly | 拒绝（复用 `ensure_writable()`） |

## 二、线程、内存、锁

| 资源维度 | 增量 | 说明 |
|---------|------|------|
| 线程 | **0** | 同步执行，无后台线程、无定时器、无异步任务 |
| 每实体常驻内存 | **0 字节** | 不记录"装载快照/旧值"（`DirtyState` 尺寸仍为 32B）；旧值由调用方显式传入 `expected` |
| 新增锁 | **0** | 复用连接池会话与既有缓存锁；锁序仍为 entity → single → field → count，无环 |
| 缓存失效 | 每次调用 1 次 | 成功与冲突都调用 `invalidate_cache`；`has_caches == false` 时是**原子读快路**（不取锁、不分配） |
| SQL 往返 | **1 次**（与 `update_by_pk` 相同） | 条件与 SET 在同一条语句内，无额外 SELECT |
| SQL 参数 | `sets.len() + expected.len() + 主键数` | 比 `update_by_pk` 多 `expected.len()` 个（通常 1 个） |

**为什么冲突也要失效缓存**：CAS 返回 0 说明「本进程读到的旧值」已经过期（别的进程写了库）。
若不失效，调用方"重读 → 合并 → 重试"会继续读回同一份旧缓存，形成永久冲突循环。
该开销只在冲突路径，且无缓存时为零成本快路。

## 三、2026-10-23 追加优化：SQL 拼接零分配

首版用 `format!` / `Vec<join>` 拼 SQL：单次 CAS 比 `update_by_pk` 多 11 次分配、+423 ns。
随后做了四项**通用**优化（不只服务 CAS）：

| 优化 | 内容 | 影响面 |
|------|------|--------|
| 追加式引用/占位符 | `DatabaseKind::push_quoted` / `push_placeholder`（无中间 String），与 `quote` / `placeholder` **逐字节等价**（单测护栏） | 所有写 SQL |
| UPDATE / 累加拼接 | `update_sql_owned_named` / `increment_sql_owned_named` / `update_if_sql_owned_named` 直接拼 `SET`，不再 `Vec<String>` + `join` + `format!` | 单行更新 / CAS / 原子累加 |
| INSERT 拼接 | `insert_sql_owned_named` 直接拼列名与占位符 | 单行插入 |
| 拦截器注册表 | `RwLock<Arc<Vec<_>>>` 快照 + `HAS_INTERCEPTORS` 原子快路：未启用时零锁零分配，启用时也不复制 Vec | 所有写路径 |

结果（`cargo test --release --test perf_guard`，事务内，2 万次，预热 2000 次）：

| 路径 | 首版 | 第一轮（SQL 拼接零分配） | 第二轮（按主键零分配） | 累计 |
|------|------|--------------------------|------------------------|------|
| 插入一行（20 列） | 9.0 µs | 4.66 µs | **4.49 µs** | **−50%** |
| `update_by_pk` | 2 074 ns | 1 422 ns | **799 ns** | **−61%** |
| `update_if` 成功 | 2 498 ns | 1 892~2 014 ns | **880 ns** | **−65%** |
| `update_if` 冲突 | 2 426 ns | 1 762 ns | **777 ns** | **−68%** |
| 批量插入摊销（5000/批） | — | 9 032 ns/行 | 8 311 ns/行 | 未改（拼接每批一次，摊销可忽略） |

### 3.1 成本拆解（第二轮优化后）

| 组成 | ns/op | 占比 |
|------|-------|------|
| 预构建 SQL 直接 `execute`（数据库 + 参数绑定） | **416.9** | 52% |
| 框架侧（SQL 构建 + 拦截器 + 缓存判定） | **≈388.3** | 48% |
| `update_by_pk` 端到端 | 805.2 | 100% |

→ 框架侧从 1 033 ns 降到 **388 ns**；CAS 相对普通更新只多 **+80 ns（+10%）**。

### 3.2 第二轮：按主键零分配（2026-10-23）

- 新增 `sqlbuild::update_by_pk_sql_owned_named`：主键条件直接拼接（`WHERE "Id" = ?`），
  不再经过 `pk_filter` 的 `Where` / `Cond` / 列名 `String` / 值 `Vec`，也不走 `filter.render` 的
  `Vec<String>` + `format!` + `join`。
- `update_by_pk_single` 与 `update_if` 全部改用它（删除 `update_if_sql_owned_named`）。
- 数据：`update_by_pk` 1 422→**799 ns**（分配 23→**10**）；CAS 2 014→**880 ns**；冲突 **777 ns**；
  框架侧 1 033.5→**388.3 ns**；`update_if` 相对普通更新 **+80 ns（+10%）**。
- 未做（§七 说明理由）：`find_by_pk` / `delete_by_pk` 主键直拼（需改 SELECT/DELETE 构建与
  拦截器 Delete 通知）、`insert_multi_sql_named`（每批一次，摊销 <1 ns/行）、
  `interceptor::prepare` 零拷贝（需改公开 trait 签名，风险高）。

**SQL 文本稳定性**：CAS 语句由「SET 列集 + 期望列集」决定。同一业务固定列集时 SQL 文本固定，
可命中 SQLite `prepare_cached`（容量 64）与其余驱动的语句缓存；**动态列集**会让语句缓存抖动，
应避免（与 `update_columns` 的限制一致）。

## 四、并发与放大分析（IoT 高并发）

- 框架侧 1.03 µs 是**每次调用的固定成本**：总开销 = 写入次数 × 固定成本，**线性**，
  不随并发线程数、表行数或数据量增长，不存在指数/平方放大。
- 单核写入上限（仅框架 + SQLite 本地执行，不含提交/网络）≈ 1 / 1.44 µs ≈ **69 万次/秒**。
- 真实瓶颈排序：**事务提交 / WAL fsync > 行锁竞争 > 网络 RTT（远程库 0.1~1 ms）> 语句缓存查找 >
  参数绑定 > 框架 SQL 拼接（~1 µs）**。所以 CAS 的 +0.3~0.6 µs 相对远程库往返 **<1%**；
  相对本地批量写，会被调用次数摊销。
- 100 万设备 × 1 次/秒 = 100 万次/秒：框架侧约 **1 核/秒**；这个量级必须用
  `insert_batch`（日志/遥测）与 `increment`（计数），CAS 只留给余额/库存/状态机等并发敏感字段。
- 连接池/锁：会话借还单线程 91.8 ns、8 线程 204.9 ns（劣化含测量噪声）；
  缓存元数据 8 线程 46.2 ns；无新增锁、无新增线程。

### 4.1 往返 / 锁 / WAL 的优化现状

| 项 | 状态 |
|----|------|
| SQLite `journal_mode=WAL` | ✅ 已默认（`sqlite.rs` 打开连接时设置） |
| `Synchronous=Off`（默认，对齐 C#） | ✅ 默认（高频写入最快）；连接串可改 `Normal/Full/Extra`，断电风险由项目自担 |
| 连接串可配 pragma | ✅ `Synchronous` / `Cache Size` / `Journal Mode` / `BusyTimeout` / `Readonly`（键名同 C#） |
| `busy_timeout=5000` | ✅ 已默认（多连接/多进程写竞争少报错） |
| 预编译语句缓存 | ✅ SQLite 64 条；MySQL `stmt_cache_size(64)` |
| 事务批处理（N 次写 1 次提交） | ⚠️ **业务侧**：`session.begin/commit` 包裹，是高并发最有效的一招 |
| 连接池分片 + 会话复用 | ✅ 快路 91.8 ns；8 线程 204.9 ns |
| CAS 的额外往返 | ✅ 无（条件与 SET 同一条语句） |
| `synchronous=OFF` | ❌ 不默认（断电会丢最近事务；XCode 生产环境如此，本库更保守） |
| `wal_autocheckpoint` / `journal_size_limit` / `cache_size` / `mmap_size` | 可选调优（大库/读多场景），非默认 |
| `expected` 列索引 | ❗ 业务约束：确保走主键/索引，否则 CAS 会全表扫描 |
| PostgreSQL / SQL Server / Oracle 语句缓存 | 待办（需真实库端到端验证） |

## 五、边界与红线

1. **`expected` 必须是"读取时的旧值"**；传实体当前值会退化为"永远成功"，失去并发保护。
2. `expected` 为空 = 等价 `update_by_pk`（无保护），不建议。
3. 批量 CAS 不在本轮范围：`update_batch`/`save_batch` 仍是"逐行覆盖自己的脏列"，
   并发敏感列请逐行 `update_if_unchanged` 或改用 `increment`。
4. 分表（`DataScale="timeShard:..."`）不支持 CAS；时序/日志表通常不需要。
5. `Version` 列方案需调用方自己维护 `SET Version = Version + 1`（可用 `update_if` 的 `sets` 传
   `("Version", 新版本)`，并把旧版本放入 `expected`）。

## 七、后续候选（按收益排序）

| 候选 | 预估收益 | 取舍 |
|------|---------|------|
| **`find_by_pk` / `delete_by_pk` 主键直拼**（同 `update_by_pk_sql_owned_named`） | −3~4 次分配、−150~250 ns | 需改 SELECT/DELETE 构建与拦截器 `Delete` 通知，下轮做 |
| `interceptor::prepare` 零拷贝（列名 `'static` 时避免 `to_string`） | −1~2 次分配、−30~60 ns | 需改公开 `EntityInterceptor` 签名，风险高，暂缓 |
| `insert_multi_sql_named` 零分配 | 每批一次，摊销 **<1 ns/行** | 不做（收益可忽略） |
| `Where` 条件的 owned 拷贝（`Where::eq_ref`） | −2~4 次分配、−50~100 ns | CAS/按主键更新已用专用拼接规避；查询路径待评估 |
| 分表 CAS 自动路由 | 覆盖时序表并发改 | 需求低（分表多为插入型），待真实场景 |
| 批量 CAS（`CASE WHEN` 单语句或逐行） | 少 N-1 次往返 | 语义复杂（部分成功/部分冲突），需单独设计 |
| `Version` 列自增封装（`update_with_version`） | 少一行手写 | 与业务字段命名强耦合，保持调用方显式 |
