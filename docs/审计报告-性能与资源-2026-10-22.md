# 性能与资源消耗审计报告（2026-10-22）

> 审计对象：本轮全部改动（脏字段更新、批量/分表写路径、缓存一致性、读写分离、InsertOnly、IsView、
> MaxCacheCount 自动缓存、FieldCache、SingleCache 接入、条件批量更新）。
> 方法：源码逐路径核对 + `tests/perf_guard.rs` 微基准（本机 release，`--test-threads=1`，统计堆分配次数）。

## 一、结论摘要

| 维度 | 结论 |
|------|------|
| **线程** | **零新增**。ORM 热路径（脏追踪/缓存/批量/队列/字段缓存）不创建线程；缓存刷新在调用方线程内完成（写锁单飞）；`EntityQueue` 无内置定时器 |
| **内存** | 每实体固定 +**32 字节**（`DirtyState`）；缓存实例 88 字节/表；`FieldCache` ≈88 字节 + ≤20 条值；`Dal` 新增表名索引（176 表 ≈28KB，一次性） |
| **CPU** | 净收益；**审计中发现并修掉 2 处真实回退**（模型表查找 9.8×、缓存失效全表扫描） |
| **数据库压力** | 下降：只写变化列、批量合并、小表查询**零 SQL**、条件更新 1 条语句替代 N 条 |

## 二、发现的问题与修复

| # | 问题 | 影响 | 修复 | 实测 |
|---|------|------|------|------|
| **P1** | `EntityModel::table()` 线性扫描（每次比较两次 `eq_ignore_ascii_case`），而热路径每次操作要查 **2–4 次**表定义 | 176 表模型：**148.5 ns/次**纯查找开销；一次 `find`/`save` 达 300–600 ns | `Dal` 内建表名索引（原名 / 物理名 / 小写三套键）+ **原名精确匹配快路径**（零分配） | **148.5 → 15.2 ns/op（9.8×）**，堆分配 **0** |
| **P2** | `invalidate_cache` 用前缀匹配**遍历全部**字段缓存 | 写操作 O(所有表 × 列) | 改两级 `HashMap<表, HashMap<列, Arc<FieldCache>>>`，只处理本表 | O(1) |
| **P3** | 行数缓存用 `Mutex`（读多写少） | 每次 `find_cached_by` 抢锁 | 改 `RwLock`（读路径并发） | 读锁 ~20ns |
| **P4** | `find` 接入 `SingleCache` 多一次注册表锁 + key 分配 | ≈70 ns/次 | 保留（缓存命中省一次 SQL 往返 10µs 级，收益远大于开销） | — |

> P1 的影响面超出本轮新功能：**所有既有实体操作**都受益（`dal.table()` 一直线性）。

## 三、逐项资源账（本轮新增能力）

| 能力 | 额外 CPU（命中路径） | 额外内存 | 数据库影响 |
|------|---------------------|----------|-----------|
| `find`（单主键 + `MaxCacheCount>0`） | 表查找 15ns + 注册表锁 ≈25ns + key 分配 ≈30ns ≈ **70ns** | 单对象缓存项（`Arc<DbRow>`） | 命中 0 次查询；未命中 1 次 |
| `find_cached_by`（唯一索引） | 行数缓存读 ≈20ns + 表查找 15ns + 注册表锁 25ns ≈ **60ns**；整表匹配 O(行数) | 整表 `Arc<Vec<DbRow>>` | 行数 < 阀值：**0 次查询**（每 60s 最多 1 次行数采样） |
| `FieldCache` | 命中 ≈50ns（内部锁 + Arc clone） | ≈88B + ≤20 条值字符串 | 每 **10 分钟** 1 次 `GROUP BY` |
| `update_where` | 1 次 bool 检查 + 拦截器 + 失效 | 无 | **1 条语句改 N 行** |
| 视图 / `InsertOnly` 拦截 | 1 次 bool | 无 | 阻止无效往返 |
| 脏追踪（字段赋值） | **35.6 ns，0 分配** | 32 B/实体 | 只写变化列 |
| 实体缓存命中 | **13.0 ns**（8 线程 **44.9 ns**） | `Arc` 快照共享 | — |

## 四、内存明细

| 项 | 大小 / 规模 | 说明 |
|----|------------|------|
| 每实体 | **32 字节**（`Option` 40） | `DirtyState`；脏项向量 `clear` 后保留容量复用 |
| `EntityCache` | **88 字节**（原 120） | 元数据由 2 个 Mutex 改原子 |
| `FieldCache` | ≈88 字节 + ≤20 条值 | 每 (表, 列) 一个 |
| `Dal::field_caches` | O(实际用到的表×列) | 两级 map，写入失效不清注册项 |
| `Dal::count_cache` | O(表数) × ~32 字节 | 176 表 ≈ 5.6KB |
| `Dal::table_index` | 4 × 表数 条字符串 | 176 表 ≈ 28KB（一次性构建；5000 表模型 ≈800KB） |

## 五、锁与并发安全

- 注册表锁彼此独立：`entity_caches`、`single_caches`、`field_caches`、`count_cache(RwLock)`；
- `invalidate_cache` 固定顺序：entity → single → field → count，**从不反向获取** → 无环；
- `field_cache()` 持注册表锁时**只 clone `Arc`**，不获取 `FieldCache` 内部锁；
  `FieldCache::items()` 持内部锁时只调 `dal.kind()`/`log_sql()`（不碰注册表）→ 无嵌套反向；
- `FieldCache::items()` 过期刷新为**双重检查 + 写锁内查库**（单飞，防击穿）；
- `EntityCache::entities()` 同样是读锁快路径 + 写锁单飞；
- `DirtyState` 为每实体独立 `Mutex`（不共享则无争用；文档要求实体不跨线程共享）。

## 六、数据库压力对比（10 万次操作估算）

| 场景 | 改动前 | 现在 |
|------|--------|------|
| 小表按唯一键查 10 万次（1000 行内） | 10 万次往返 | **0 次**（首次 1 次整表加载 + 每 60s 1 次行数采样） |
| 批量改状态（10 万行同值） | 10 万次 UPDATE | **1 次** `UPDATE ... WHERE` |
| 日志表插 10 万行 | 10 万次 INSERT（每次判存在性） | **20 次**批量 INSERT（5000/批，`InsertOnly` 不判存在性） |
| 更新一行 5 个字段 | 写全部列 | **只写变化列**（WAL/binlog/复制量按列数缩减） |
| 下拉分类选项 | 每次请求 `GROUP BY` | 每 10 分钟 1 次 |

## 八、结论与建议

1. **可放心用于高并发与海量设备场景**：无新增线程、热路径零分配、缓存失效 O(1)、注册表不随写入增长。
2. **仍需业务侧遵守的边界**（已写入 `docs/使用规范.md`）：大表禁整表缓存、实体即用即弃、
   实体不跨线程共享、会话按线程、避免长事务、批量写优先。
3. **后续可选**：`Fields` 静态列元数据（纯 DX）、`Valid` 校验链（业务校验），
   均不影响当前性能与资源。
4. **维护纪律**：改动 `dirty.rs` / `cache.rs` / `session.rs` / `entity.rs` 写路径或 `dal.rs` 的
   表查找/缓存注册后，必须重跑上述基准并对比本报告数字。

## 补充（第十一轮）：`Valid` 校验链的资源开销

- **位置**：`insert` / `update` / `insert_sharded` 进入 SQL 之前；纯内存判断，**零分配**（`trim().is_empty()` 只读切片）。
- **量级**：每个必填列 1 次空白判断（纳秒级），与一次数据库往返（数十微秒~毫秒）相比可忽略；**只在写入路径**，读路径完全不受影响。
- **跳过逻辑**：有脏追踪的实体在 `!has_dirty()` 时直接返回（一次原子/锁读），因此「读出对象但没有改动」的场景没有额外成本。
- **批量路径**：`insert_batch` / `save_batch` **不逐条校验**（保持批量语义与吞吐），校验成本为 0。
