## 2026-10-22 实体脏字段更新（写入最小化，对齐 C# `Dirtys`）

- **用户原话**：
  - 「当前这个 Pek.RCode 是否有实现数据库数据写入时如果字段数据没有变化不会重复写入，而且根据实际不会针对所有的字段都每次全部都写入吧。因为要考虑减少不必要的数据库写，另外读是有和 DH.NCode 一样有缓存的吧」
  - 「哪一种性能更好，能减少数据库的压力以及提升应用系统的性能更优且更统一方便，既然封了库那肯定是要尽量减少每个业务系统的维护成本以及统一开发代码」
  - 「需要的」
- **现状核查结论**：写入侧实体层每次 UPDATE 全部非主键列、无变化也发 SQL（`DirtyCollection` 已移植但未接线）；读取侧缓存体系完整（`EntityCache` 60s / `SingleCache` 60s / `FieldCache` 600s / 写后自动失效）。
- **方案取舍**：采用 **B（实体自动脏追踪）**。A（显式列集）把"写哪些列"的责任下放给业务，漏列即静默丢更新；C（可选 setter）是双轨制、依赖纪律。B 的数据库侧效果与 A 相同（只写变化列、无变化 0 SQL），而业务只需"赋值 → save"，所有项目统一受益。
- **实现口径**：
  - `dirty.rs` 新增 `DirtyState`（`Mutex<DirtyCollection>`；线程安全，`&self` 可读写；`Clone` 复制脏项、`PartialEq` 恒等——脏状态属元数据，不参与实体相等性）。
  - `Entity` trait 新增 `dirty_state()`（默认 `None`）、`is_dirty` / `has_dirty` / `clear_dirty`；`update_with` 在启用脏追踪时空脏直接返回 0、只拼脏列、执行后清空；`insert_with` / `write_batch_refs` 成功后清空；`enqueue_save` 在启用脏追踪且无脏时跳过入队（有脏仍传全列——Upsert 的插入分支需要）。
  - `codegen` 生成的实体字段**私有**，提供 `列名()` / `set_列名()`（setter 比较新旧值，相同不标脏）与私有 `dirty` 字段；`generate_interface` 只输出 trait 契约（跨模块无法访问私有字段），不再生成 impl。
  - **审计列口径**：业务列无变化时整条跳过，不刷新 `UpdateTime`（与 C# `if (!entity.HasDirty) return 0;` 一致）。
  - **兼容**：手写实体与 `#[derive(Entity)]` 实体 `dirty_state()` 默认 `None`，仍写全部非主键列；需要优化时自行实现 `dirty_state()`。
- **破坏面**：当时消费方无任何生成实体（全部 `dal.table(...)` + `update_by_pk`），无迁移成本。
- **验证**：库内 259 项 + 全部集成测试全绿、clippy 零告警；新增两项行为测试（两会话交叉更新证明未变化列不被旧值覆盖；同值赋值不标脏且无脏 `update` 返回 0）；`rcodegen` 生成的 entity + interface 在独立 crate 中 `cargo check` 通过。

## 2026-10-22（二）批量/异步/分表路径统一 + 性能调优

- **用户原话**：「目前还有其他类似可以优化调优的地方么？性能是肯定要考虑到的。而且也要注意弄这个 ORM 就是要尽可能的避免因为每个人的能力不同而导致的使用问题。还有那些 list.save 等以及 saveasyc 等是不是也有相同的逻辑实现。你不能仅仅只考虑 update 和 save 这两个吧，以及分库分表那里相关的也要同样考虑」
- **覆盖范围核查**：save/update/update_batch/update_sharded/save_batch/save_batch_sharded 已走脏列；insert_batch_sharded/upsert_batch_sharded 缺「成功后清空脏」；enqueue_save（SaveAsync）有脏时仍全列；upsert_batch* 为 SQL 级整行覆盖（保留并在 README 说明）。
- **本轮实现**：
  - 分表批量写入（write_batch_sharded_refs）成功后清空各实体脏数据；delete_with 后清空。
  - EntityQueue 新增 upsert_tracked（记录脏列）：enqueue_save 的 Upsert 更新分支只写脏列，行不存在仍插入全列；无脏不入队。
  - 新增 Entity::update_columns（显式列集，对应 C# Update(names, values)）：只写指定列，成功后只清除这些列的脏标记；未知列报错。
  - 性能：Entity::column_value（生成实体按列直接取值）+ update_with 按脏列取值（宽表不再全字段克隆）；save_batch 无自增+单主键一次 IN 判定存在性；DbRow::get_by_name 列名索引缓存（消除 O(列数²) 装载）。
  - 防呆：文档明确「启用脏追踪必须经 setter 修改」；生成实体字段私有（编译期防误用）。
- **验证**：新增测试覆盖显式列集/批量插入清脏/队列脏列/DbRow 索引/分表脏逻辑；全量测试全绿、clippy 0 告警。

## 2026-10-22（三）后续优化候选落地（1/2/3/5；4 有意不做）

- **用户原话**：「继续」（续做上一轮列出的 5 项后续候选）。
- **落地**：
  1. save_batch_sharded 存在性判定：无自增 + 单一主键时按 (连接, 物理表) 分组，每组一次 IN 查询（分块 1000，跨库自动路由）；复合主键仍逐条点查。
  2. insert / update_by_pk 热路径改 owned 列集合（interceptor::prepare_owned + sqlbuild::{insert,update}_sql_owned_named，值直接移入 SQL 参数）：单行插入/更新各少一次全列克隆；新增 TableRef::insert_owned。
  3. `DbRow` 列名索引由 `RowSet` 统一构建一次、各行共享（`DbRow::with_index`）；`RowSet::column_index` 走同一索引。
  5. 实体缓存过期语义改为「旧值 + 延迟刷新」：首次发现过期返回旧数据（不阻塞），下次访问同步刷新；`invalidate` / `reload` 重置标记（`Dal` 非跨线程共享，故不用后台线程）。
- **有意不做**：4. EntityQueue Update 段批合并——SQL 无通用多行 UPDATE，CASE WHEN 方案语句膨胀且方言差异大；逐条与 C# 一致，保持。
- **验证**：全量测试（lib 259 + 集成）全绿、clippy 0 告警；cache::tests::expire_reloads_when_elapsed 更新为两次访问（旧值 → 刷新）。

## 2026-10-22（四）缓存一致性模式 + 多行 UPDATE 评估

- **用户原话**：「像这种我记得每个数据库会有一个专门的组件的，那是不是要结合每一种库的组件来调整实现？」以及「实体缓存过期后第一次读返回旧值（不阻塞），下次访问刷新——需要即时最新值时请显式 reload 这种对于实际业务逻辑有更合适的么？也不是一定非要完全按C#的。但我需要根据不同的应用场景来判断处理，要不然会不会有可能有强一致的数据有影响？」
- **缓存（已实施）**：新增 `CacheConsistency`——
  - `Blocking`（**默认**）：过期即同步重载，强一致安全；
  - `StaleWhileRevalidate { max_stale }`：过期后在窗口内先返回旧值、下次访问刷新，超过窗口同步重载；
  - `EntityCache::set_consistency` / `consistency()`；写入自动失效不变。
  - **默认从上一轮的延迟刷新改回 `Blocking`**（安全优先），SWR 需显式开启；README 增加「缓存选型建议」。
- **多行 UPDATE 评估（待确认是否实施）**：
  - `dbserver-*` 组件只是驱动宿主（负责连接/执行），**SQL 方言在 `dialect.rs` / `sqlbuild.rs`**，不需要"结合组件"，应为 `sqlbuild` 增加 `multi_update_sql_named` 的方言分支，所有连接方式共享；
  - 方言矩阵：PostgreSQL `UPDATE ... FROM (VALUES ...)`；SQLite 3.33+/DuckDB `UPDATE ... FROM`；SQL Server `UPDATE ... FROM ... JOIN (VALUES ...)`；MySQL 8.0.19+ `UPDATE ... JOIN (VALUES ROW ...)`（MariaDB 用 `SELECT ... UNION ALL` 派生表）；Oracle/DB2 用 `MERGE`；其余回退逐条；
  - 前提：按「更新列集」分组（同列集才能合一条）、单/复合主键 JOIN；收益 N 行 → 组数（通常 1）次往返；
  - 建议：先做 5 个主流方言（PG/SQLite/DuckDB/SQL Server/MySQL）并以回退兜底，需要独立一轮 + 各库实测（本机可实测 SQLite/MariaDB，其余靠语法单测或临时实例）。
- **验证**：缓存 17 项测试全绿（含新 SWR 用例）；全量测试全绿、clippy 0 告警。

## 2026-10-22（五）整表缓存的数据库压力与并发击穿

- **用户原话**：「过期即同步重载对于性能的影响大吗？或者说对于数据库的压力大吗？」
- **压力评估**：`EntityCache` 只在**有访问时**触发整表 `SELECT *`，每表每 60s 至多一次——
  - ≤1000 行小表（DH.NCode 建议的缓存表规模）：本地 SQLite <1ms、内网 MySQL 几 ms，每 60s 一次，可忽略；
  - 万行以上表：一次整表传输/解析在几十 ms 级，首次访问延迟明显 → 不建议整表缓存；
  - **两个放大器**：① 并发过期时多线程同时重载（缓存击穿）；② 写频繁的表每次写入都 `invalidate`，导致每次读都整表重载。
- **本轮修复**：`EntityCache` 状态改 `RwLock` + `stale_served: AtomicBool`——重载在**写锁内**执行，
  并发过期只有一个线程查库、其余线程等待后直接复用新数据（单飞，无击穿）；快路径仍走读锁。
- **口径**：默认 `Blocking`（强一致）；SWR 需显式开启；写频繁/大表不用整表缓存；跨进程实时性用短过期或直查。
- **验证**：缓存 18 项测试全绿（新增 8 线程并发过期用例）；全量测试全绿、clippy 0 告警。

## 2026-10-22（六）DH.NCode 读写分离核实 + 本轮改动性能回退排查

- **用户原话**：「我记得DH.NCode是不是可以配置专门是对还是专门是写或者是读写链接的？当前最新的实现对于性能是不是会导致大幅下降？」
- **DH.NCode 事实（已核源码，非猜测）**：确有读写分离，靠**连接名约定**配置——
  - 主连接名为 `X` 时，配置文件中存在 `X.readonly` 即启用单从库（`DAL.cs:160-176`）；
  - 多从库：`X.readonly.rd0`、`X.readonly.rd1`…（最多 32 个），`ReadWriteStrategy.TryGet` **轮询**分配；
  - 走向：`ReadWriteStrategy.Validate` 只在**非事务**且动作为 `Select`/`SelectCount`/`Query`（或 `ExecuteScalar` 且 SQL 以 select 开头）时切从库；可配 `IgnoreTimes`（如 00:30-00:50）与 `IgnoreTables`；
  - 即"读写连接"不是同一实体自动双写，而是**读操作分流到只读连接集合**，写永远走主连接。
- **Pek.RCode 现状**：**没有读写分离**（`Dal` 单连接 + `Databases` 多数据源 + `shards::register_connection` 分库路由），所以读全部落主库。这是**功能缺口**，与本轮优化无关。
- **本轮（脏写/批量/缓存四轮改动）性能影响核查**：
  - 写路径：净收益（只写脏列、owned 列集合少一次全列 clone、`save_batch` 单主键改一次 `IN` 判存在性、分组批量）。
  - 读路径：缓存命中为 `Arc<Vec<DbRow>>` clone（O(1)）+ 两次短 Mutex 取过期与模式（~20ns）+ 一次 `RwLock` 读锁；相比改造前多 ~20–30ns 量级，**不构成"大幅下降"**；并发过期由写锁单飞，反而**消除击穿**。
  - **发现并修复一处真实回退**：`DbRow::get_by_name` / `RowSet::push` 此前**无条件**构建列名 HashMap 索引——单行/少列（≤8 列）时反而比线性 `eq_ignore_ascii_case` 慢（多一次分配）。现改为
    `SMALL_COLUMN_COUNT = 8`：列数 ≤8 走线性比较、不建索引；宽表仍共享索引。`RowSet::column_index` 同步处理。
- **读写分离若要实现（本轮不做，待确认）**：Pek.RCode 的 session 模型是"业务先 `dal.open_session()` 再传引用给 `TableRef`"，与 C# `DAL` 内部包装 SQL 不同——
  - 需要 `Dal.reads: Vec<Arc<Dal>>` + `Dal::read_session()`（轮询）；
  - 事务内不切换需要 `SqlSession::in_transaction()`（各驱动已有事务状态可暴露，默认 false 向后兼容）；
  - 忽略表/时间段策略、缓存加载走从库还是主库（主从延迟会让缓存带旧值，C# 亦如此）需一并定口径；
  - 工作量中等，建议独立一轮并配套主从实例实测。
- **验证**：`cargo test --lib --tests` 全绿；`cargo clippy --all-targets` 0 告警。
## 2026-10-22（七）高并发/海量设备场景的资源核查与热路径再优化

- **用户原话**：「当前的所有这些调整优化有没有可能会导致应用所需要的CPU资源、内存资源以及线程占用数等都会更高？因为我们的应用系统是高并发的，有应用到物联网平台，可能会连接数百万甚至上亿的设备，这个对于性能的要求就比较高，而且对于数据库的压力也是非常之大的。」
- **线程**：核查 `src` 全部 `thread::spawn` —— ORM 热路径（脏追踪/实体缓存/批量写/队列）**零线程**；
  `cache.rs` 唯一的线程在 `#[cfg(test)]`（并发过期用例），其余分别属于 `db_service`（驱动宿主参考实现）、
  `driver_pack`（拉起 dbserver 子进程）、`network`（远程协议服务端）、`store`（测试）。
  缓存过期刷新在调用方线程内完成（写锁内单飞），`EntityQueue` 无内置定时器 → **线程占用不因本轮改动增加**。
- **内存**：`size_of::<DirtyState>() = 32`、`Option<DirtyState> = 40`、`EntityCache = 120 → 88`（元数据由 2 个 Mutex 改原子）。
  实体只内嵌 `DirtyState`（无 EntityExtend 常驻）；脏项向量 `clear` 后保留容量复用。
- **发现并修掉的两处真实热点（基准为证）**：
  1. 脏列名每次赋值 `to_string()` 分配 + `names()` 再为每列分配一个 String ——
     改 `Cow<'static, str>` + `mark_static()`（生成实体传字面量，零分配）+ `DirtyState::with_columns()` 持锁遍历
     （`update` 不再构造列名列表）。代码生成器 setter 改 `self.dirty.mark_static("列名")`。
  2. 缓存/单对象缓存的 `expire` / `consistency` 是 Mutex，命中路径每次 2 次加锁 →
     改 `AtomicU64`（纳秒）/`AtomicU8`（模式）+`AtomicU64`（SWR 窗口），命中路径只剩一次 `RwLock` 读锁。
- **实测**（`cargo test --release --test perf_guard -- --ignored --nocapture --test-threads=1`，同二进制对照）：

  | 场景 | 优化前 | 优化后 |
  |------|--------|--------|
  | 单列脏登记 + 清空 | 65.3 ns / 1 次分配 | **35.6 ns / 0 次分配** |
  | 典型保存周期（5 列） | 520.0 ns / 12 次分配 | **137.6 ns / 0 次分配** |
  | 缓存元数据读 | 38.7 ns（2 Mutex + RwLock） | **13.0 ns** |
  | 缓存元数据读 × 8 线程 | 208.1 ns（争用 5.4×） | **44.9 ns** |

- **数据库压力定位**：本轮改动的价值在"少写 / 少锁 / 少分配"，不改变访问模式；
  真正的压力来自错误用法（大表整表缓存、逐条 save、长事务）——已在 README 新增
  「资源占用与海量数据边界（高并发 / 物联网场景）」章节写明 7 条边界与选型建议。
- **有意不做**：`enqueue_save` 的列名 String 分配（该路径本就为每条记录构造完整 `fields` 的 owned String，
  只优化列名收益可忽略；超高吞吐场景文档建议直接用 `insert_batch` / `upsert_batch` / `save_batch`）。
- **验证**：新增 `tests/perf_guard.rs`（6 项 `#[ignore]` 基准：脏登记/保存周期/探查/缓存命中/并发读/尺寸）；
  lib 262 项 + 全部集成套件全绿、`cargo clippy --all-targets` 0 告警。
## 2026-10-22（八）读写分离落地 + 表级「只读」真相核实 + 使用规范

- **用户原话**：「Pek.RCode 也要实现读写分离，另外我记得C#中如果配置了某个表只读，那这个性能会更高，是真有这种逻辑么？另外当前这个Pek.NCode是不是要有一个使用规范，其他项目在使用这个库时要先读这个规范来避免你所提出的这些问题，尽可能的减少人为错误。」
  追加：「但我明明记得可以针对每个表单独设置是否只读的啊。」
- **核实结论（源码为准，非猜测）**：DH.NCode 的"只读"共有四类，**没有"表级只读数据"**：

  | 类别 | 位置 | 语义 | 性能影响 |
  |------|------|------|---------|
  | **`<Table InsertOnly="True">`** | `ModelSchema.xsd`（"仅插入数据，比如日志表、记录表、事件表等"） | 表级：`Entity.DoAction` 拒绝 Update/Delete（"只写的日志型数据禁止修改/禁止删除！"）；`EntityQueue.flush` 走 `batch.Insert` 而非 `Save`；`EntityBuilder` 跳过相应代码生成 | **真实收益**：保存不查主键存在性 → 每行省一次查询 |
  | `<Table Migration="ReadOnly">` | `ModelSchema.xsd:281` | 表级结构迁移：只生成 DDL 不执行 | 只影响迁移阶段，不影响 CRUD |
  | 连接 `Readonly=true` | `DbBase.Readonly` / `DAL_DbOperate` | 连接级：写语句/事务**在调用点抛异常**（不发 SQL） | 省一次数据库往返的错误路径；SQLite 不设 WAL |
  | `FieldItem.ReadOnly` | `Configuration/FieldItem.cs` | 字段级：仅代码生成/界面（无 setter） | **不影响 SQL 列数** |

  即用户记的"针对每个表单独设置"= **`InsertOnly`**（日志/记录/事件表），"性能更高"= 跳过存在性查询。
- **实现一：读写分离**（新模块 `src/readwrite.rs` + `Dal` 扩展，对齐 C# `DAL.Reads` / `ReadWriteStrategy`）：
  - 连接名约定同 C#：`X.readonly`（单副本）/ `X.readonly.rd0..rd31`（多副本），
    `Dal::read_replicas_from_file(&DatabaseFile, base, "X")` 自动发现并实例化；
  - `Dal::attach_read_replicas / read_replicas / has_read_replicas / read_session()`（轮询；
    无副本、副本创建失败均**回退主库**）/ `read_session_for(table)`（忽略表 + 全局开关判定）；
  - `set_ignore_tables / ignored_tables / set_primary_only / is_primary_only`（忽略表即"写后立刻要读最新值"的表）；
  - **连接只读**：连接串 `Readonly=true` → `open_session` 返回 `ReadOnlySession` 包装，
    `execute`/`begin` 直接报错、不发 SQL（对齐 `if (Db.Readonly) throw`）；`is_readonly/set_readonly` 运行期切换；
  - 与 C# 差异：**不提供 `IgnoreTimes`**（时段判定依赖本地时区且主从延迟是持续问题），

- **用户原话**：「怎么缺这么多，目前还有哪些缺的，感觉你缺的都是与业务有关也能提升性能的」

  1. **`MaxCacheCount`**（`TableMeta.max_cache_count`，缺省 1000）：解析/写出往返；
     **含 `DataScale="time"` / `timeShard` 列的表强制 0**（对齐 `EntityBuilder.Prepare` 的"大表不缓存"）。

     （与 `COLLATE NOCASE` / C# `EqualIgnoreCase` 一致）。
  4. **codegen 生成 `find_by_xxx`**：遍历 `Model.xml` 的 `Unique` 索引（列需全部非空、跳过主键索引），

     —— 对齐 C# `EntityBuilder` 生成的 `if (Meta.Session.Count < MaxCacheCount) return Meta.Cache.Find(..)`。
- **仍存在的差距（已写入 README「与 DH.NCode 的已知差距」表）**：
  `FieldCache<T>`（按列分组缓存 + 下拉选项）、`SingleCache` 未自动接入按主键查询、`DbCache`（SQL 结果缓存）、

## 2026-10-22（十）FieldCache / 单对象缓存接入 / 条件批量更新 + 性能与资源审计

- **用户原话**：「请继续」「弄完之后要做全面审计，重点要关注一下性能以及资源消耗是否有影响。」
- **补齐三项（此前盘点出的高优先缺口）**：
  1. **`FieldCache`**（`cache.rs`）：按列分组统计（`COUNT(*) GROUP BY 列 ORDER BY c DESC`，默认前 20、缓存 600s），

  3. **条件批量更新**：`TableRef::update_where(sets, filter)` + `Entity::update_where`——
     `UPDATE ... SET ... WHERE ...` 一条语句改多行（批量改状态/打标），比逐行少 N-1 次往返；
     视图/仅插入表拒绝、拦截器刷新审计字段、写入后缓存失效。
- **全面审计（性能与资源）**：见 `docs/审计报告-性能与资源-2026-10-22.md`。**审计中发现并修掉 3 处回退**：
  - **P1（最大）**：`EntityModel::table()` 线性扫描被热路径每次操作调用 2–4 次，
    176 表模型 **148.5 ns/op**；改为 `Dal` 内建表名索引（原名/物理名/小写三套键）+ 原名精确匹配快路径

  - **P2**：`invalidate_cache` 用前缀匹配遍历全部字段缓存（写操作 O(所有表×列)）→ 改两级 map（表→列），O(1)。
  - **P3**：行数缓存 `Mutex` → `RwLock`（读多写少，`find_cached_by` 每次都要读）。
- **审计结论**：线程 **零新增**；每实体 +32B；`FieldCache` ≈88B + ≤20 条值；`Dal::table_index` 176 表 ≈28KB（一次性）；
  锁序固定（entity→single→field→count，不反向获取）无环；`FieldCache` 过期刷新为写锁内单飞（防击穿）。
  数据库压力对比（10 万次）：小表按唯一键查询 10 万次往返 → **0 次**；批量改状态 10 万条 UPDATE → **1 条**。

  `entity_layer` 新增 `update_where`（单语句多行）与 `find` 单对象缓存（写入后读到新值）用例；
  `model_e2e` 断言生成 `find_by_xxx` + `xxx_list`；`perf_guard` 新增「模型表查找」基准。

## 2026-10-22（十一）补齐 `Valid` 校验链（含生成代码编译验证抓到的 1 个 bug）

- **用户原话**：「请继续补」
- **目标**：把差距表里最后一块**业务价值最高**的能力补上——逐实体 `Valid` 校验链（C# `Entity.Valid`）。

### 实现（对齐 DH.NCode 生成代码，非猜测：已读 `Entity.cs` + `EntityBuilder.BuildValid`）

## 2026-10-22（十二）端到端热路径审计：语句缓存 / 池分片 / 零分配读路径

- **用户原话**：「弄完之后要做全面审计，重点要关注一下性能以及资源消耗是否有影响。看是否还有性能提升以及资源占用降低的可能性。以及要考虑百万级以上的设备高并发场景下的应用支持」
- **做法**：先**新增端到端基准**（`perf_guard.rs` 第二组：会话借还、行取值、写/读往返），测出基线，再逐项优化、逐项复测。不凭感觉改。

### 基线暴露并修掉的 6 处（全部有前后实测数字）

| 编号 | 问题 | 修复 | 前后 |
|------|------|------|------|
| **E1** | SQLite 每次执行都重新编译 SQL | `prepare_cached`（容量 64）+ 参数走 `ValueRef` 借用（Text/Blob 不再复制） | 插入 13,917→**9,012 ns**；查询 16,020→**6,336 ns** |
| **E2** | 连接池单一 Mutex + 3 个全局原子计数 → 高并发串行 | 空闲队列**按线程分片**（CPU 核数 2–16 片，线程本地缓存偏好分片），统计计数分片化 | 8 线程 650.4→**194.2 ns（3.35×）**，劣化 4.4×→**1.28×** |
| **E3** | 宽表按列名取值每次 `to_ascii_lowercase()` 分配 | 列名索引**原文+小写双键**（原文命中零分配），且索引由结果集共享、**首次取值才构建** | 55.7→**17.1 ns**，分配 200 万→**0** |
| **E4** | 读会话获取克隆副本 `Vec` + 策略锁 + 小写化 | 副本列表改 `Arc` 快照；`has_replicas` / `rw_needs_check` 原子短路 | 209.6→**166.6 ns**，分配 2→**1** |
| **E5** | 批量写入每行每列线性查列名（20×5000=200 万次比较） | 按首行算一次「列→位置」，后续行按位置取（列集不一致时自动回退按名查） | 11,139→**9,492 ns/行**，分配 106→86 |
| **E6** | 每次写入都做 4 次锁的缓存失效（即使从没用过缓存） | `has_caches` 原子标志，从未注册缓存时直接返回 | 写路径 4 锁 + 1 分配 → **0** |

### 关键结论（回答用户的三个问题）

1. **是否对性能/资源有影响**：此前几轮改动**没有回退**（脏追踪/缓存/批量都在基准内且零分配）；
   但**端到端路径**确实存在上述 6 处历史遗留瓶颈，本轮已全部修掉。
2. **是否还有提升空间**：本轮后读路径已**零堆分配**，写路径框架开销占比 <15%（其余是 SQLite 执行）。

   已逐项评估，**收益 < 5%~15% 但需破坏公开 API 或改 16 个驱动**，明确暂不做（写入审计报告 12.5）。
3. **百万级设备高并发**：线程**零新增**；高并发争用点从「1 把全局池锁」变成「每线程 1 个分片锁」，
   8 线程吞吐劣化从 4.4× 收敛到 **1.28×**（可随核数线性扩展）；每个连接额外占用语句缓存（≤64 条）。
   ORM 侧硬指标已满足：**读路径不分配、并发不争用**。

## 2026-10-22（十三）其它驱动对齐 + 池开销拆解 + `AdditionalFields` 原子累加

- **用户原话**：「请继续，而且要判断及处理其他数据库的是否也有前面所有的支持。另外是否还有其他要从DH.NCode中做迁移的。另外池开销可以节省掉来提升性能么？」

### 一、其它数据库驱动是否也有前面的支持（逐驱动核对 + 补齐）

| 驱动 | 语句缓存 | 参数借用（免复制） | 本轮改动 |
|------|---------|------------------|---------|
| SQLite | ✅ `prepare_cached`(64) | ✅ `ValueRef` | —（上轮已做） |
| **MySQL** | ✅ crate 内建 | ❌（crate 要求 owned） | **`stmt_cache_size(64)`**（原用缺省值） |
| **PostgreSQL** | ❌（见"未做"） | ✅ **本轮** | `PgParam<'a>(&DbValue)` 免克隆 + `Text` 直接写字节（单行 20 列文本**少 40 次分配**） |
| **SQL Server** | ❌ | ✅ **本轮** | `MssqlParam<'a>(&DbValue)` 免克隆 |
| Oracle | ❌ | ❌（`Box<dyn ToSql>` 接口限制） | 保留（无消费方） |
| ODBC/HANA/CH/Influx | N/A（内联字面量） | N/A | — |

**未做（明确原因）**：PG/MSSQL/Oracle 的**语句缓存**需自维护 `HashMap<sql, Statement>`，
涉及服务端 prepared-statement 上限与 deallocate 管理，且**当前没有真实 PG/MSSQL 环境可端到端验证**
（4 个 Rust 消费方全部用 SQLite）。已写入审计报告 13.4 作为待办。

### 二、池开销能不能省掉（用户直接提问）

**做了拆解基准**（`tests/pool_bench.rs`）：152 ns 中 **`Instant::now()` ×2 = 118.4 ns（78%）**，
Mutex+队列仅 22.6 ns，`Box::new` 与 `thread_local` 实测 0 ns。
→ 把两次取时间换成 **`coarse_now_ms()`**（Windows `GetTickCount64` ≈0.7 ns / Unix epoch+elapsed），
空闲超时按毫秒判定（30s 超时足够）。

- 会话借还（单线程）：151.8 → **90~93 ns（1.66×）**；读会话获取：166.6 → **96.4 ns（1.73×）**
- 8 线程：194~247 → 207~281 ns（**噪声区间重叠**，8 线程基准自带 ±25% 波动）

**结论（为什么不彻底"省掉池"）**：
1. 去掉池 = 每次新建连接（SQLite ≈100 µs、MySQL/PG 握手更贵）→ **贵 1000 倍**，不可行；
2. 剩余 91 ns 里 Mutex 占 22 ns，改「线程本地会话缓存」最多省这 22 ns，
   却要处理线程退出归还、会话分布不均、多 Dal 实例 key → **风险远大于收益，明确不做**；
3. 91 ns 相对一次 SQL 往返（6~9 µs）占 **1.3%**，已到合理下限。

### 三、DH.NCode 还有什么是没迁移的

逐文件核对全部 `.cs`，**唯一还缺的高价值能力是 `AdditionalFields`（原子累加）**，本轮补上：

- `sqlbuild::increment_sql_owned_named`：`UPDATE t SET "Count" = "Count" + ?, "UpdateTime" = ? WHERE ...`
- `TableRef::increment` / `increment_by_pk` / `Entity::increment`（累加后把新值同步回对象）
- 拦截器补的 `UpdateTime` 自动归入「普通赋值」分支（不进累加）
- 测试 `tests/increment.rs` 3 项：多次累加正确、主键不存在返回 0、条件累加一条语句改多行、实体对象同步
- **IoT 场景刚需**：计数器/流量累计必须库内累加，否则并发丢更新（读-改-写）

其余未迁移项（`ValidHelper`/`KeyedLocker`/`SearchBuilder`/`WindowFunction`/`Linq`/`Membership`/`DbCache`/`Fields`/`LongCount`）
均为「.NET 生态特有」或「Rust 有更直接替代」，已写入 README 差距表（标"有意不做"与理由）。

### 验证
