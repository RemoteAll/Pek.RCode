# 审计报告：透明时间分表（`DataScale="timeShard:..."` 自动路由）

- 日期：2026-10-23
- 范围：`pek-rcode`（`model` / `dal` / `shards`）
- 触发：HlktechIoT Rust 侧模型对照时发现「`timeShard` 需显式 `*_sharded` API，与 C# 自动路由不一致」

## 1. 背景与判断修正

首轮判断「YRY 53 张表零张使用 `timeShard` → 暂不做」只覆盖了单一项目。全组核查后修正：

| 位置 | 用法 |
|---|---|
| `DH.NStardust/Stardust.Data/Monitors/Model.xml` | 2 处 `DataScale="timeShard:dd"`（生产项目） |
| `DH.NCode/XUnitTest.XCode/TestEntity/Model.xml` | `timeShard:yyyy` |

结论：这是**通用能力且已有生产使用**，作为 `DH.NCode` 的 Rust 实现必须补齐。

## 2. C# 参考语义（逐条对齐）

| C# | 语义 | Rust 落地 |
|---|---|---|
| `EntityBuilder.BuildShardPolicy` | `DataScale="timeShard:表段[:连接段]"` → `TablePolicy="{0}_{1:表段}"`、`ConnPolicy` 同理 | `TableMeta::shard_spec()` → `ShardSpec{field, table_policy, conn_policy}` |
| 步进推断 | `HH`→1 小时、`dd`→1 天、`MM`→30 天、`yy`→365 天、其余 1 天 | `ShardSpec::to_policy()` 同规则 |
| `Shard(entity)` | 分表字段值路由 | `insert` / `insert_owned` / `write_batch` |
| `Shards(expression)` | 条件推导分片（`= / > / >= / < / <= / BETWEEN`） | `query` / `count` / `delete_where`（复用 `shards_of_trim`） |
| `where == null` 不走分表 | 无条件查基础表 | 同（`query_sharded` 空分片回退单表） |
| `Shard(Int64)` | 雪花 Id 解析时间 | `update_by_pk` / `delete_by_pk` |
| `BatchInsert` 分表分支 | 按分片分组后批量写 | `write_batch` 分组（`ShardBatchRows`） |
| `Meta.InShard` 防递归 | 分表上下文标记 | **`Dal::table_as` 恒不分流**（显式物理表即"已在分片中"） |

| 文件 | 改动 |

## 4. 兼容性

- **显式 API 全部保留**：`*_sharded`、`query_sharded` / `count_sharded` / `delete_sharded` / `auto_shard` / `drop_shards` 行为不变，双轨并存；
- **非分表表零语义变化**（HlktechIoT 三表、Pek.RAgent、DHDeploy 均无 `timeShard`）；
- `TableRef` / `Dal` 私有字段变化不影响外部（结构体字面量无法从外部构造）；
- `TableMeta` 未加字段（规格通过方法计算 + `Dal` 缓存），不影响手写 `TableMeta` 的测试/消费方。

## 6. 性能

| 路径 | 额外开销 |
|---|---|
| 非分表表（绝大多数） | `Dal::table()` 一次 HashMap 查找（~20ns）；每次 CRUD 一次 `Option` 判空 |
| 分表表写入 | 与显式 `insert_sharded` 相同（一次策略计算 + 一次 `table_exists` 检查） |
| 分表表查询 | 与显式 `query_sharded` 相同（跨表续页逻辑未改） |
| 批量写入 | 分组一次遍历 + 每行一次 `shard_of_value`（C# 同样逐实体计算） |
| 内存 | 每张分表表一个 `Arc<ShardSpec>`（≈100B）；非分表表零占用 |

## 7. 边界与风险

1. **无条件查询查基础表**：与 C# 一致；若业务历史数据在基础表，该行为是"兼容"而非"遗漏"。
2. **自增主键 + 时间字段分表**：`update_by_pk` / `delete_by_pk` 无法从主键推时间 → 报「分表策略因条件不足无法执行分表操作！」（C# `Shards(expression)` 同样抛错）。请改用带时间条件的 `update_where` / `delete_where`。
3. **`write_batch` 分组会克隆行**：与 C# 分表批量一致（分组必然复制），单表批量路径零克隆。
4. **`dd` 段的原始语义**：`timeShard:dd` 生成 `X_01`~`X_31`（.NET `dd` = 两位日），与 C# 完全相同；需要"年月日全名"请写 `timeShard:yyyyMMdd`。
5. 跨连接分片（`ConnPolicy`）复用既有 `resolve_table_dal`（已注册连接优先，未注册自动 SQLite），透明路径同样生效。

## 8. 实体层（`Entity` trait）同样透明

`Entity::insert / update / delete / find / query / count` 内部全部经由 `dal.table(Self::table())`，
因此**自动继承表级分流**（已由 `entity_layer_inherits_transparent_sharding` 验证）。
`Entity::find(pk)` 额外走 `find_by_pk`（已按雪花主键解析路由），无法从主键推时间时回落模型默认表（同 C#）。

## 9. 后续（不在本轮）

- `sync_schema` 按 `ConnName` 分流建表（与分表无关，另一议题）。
- 分表实体的 `find_by_xxx`（唯一索引）在无时间条件时仅查默认表 —— 与 C# `FindByXxx` 相同，需要走分表请带时间条件或使用显式 `*_sharded`。
