## 十二、第十一轮审计：端到端热路径复核（2026-10-22 下午）

> 触发：用户要求「全面审计，重点看性能与资源消耗是否有影响，是否还有提升与降低的可能性，
> 以及百万级设备高并发场景的支持」。
> 方法：**新增端到端基准**（`tests/perf_guard.rs` 第二组）——会话借还、行取值、写读往返；
> 先测基线、再逐项优化、每项优化后复测，数字均为本机 release 实测。

### 12.1 基线暴露的 4 个真实瓶颈

| # | 瓶颈 | 实测（优化前） | 影响面 |
|---|------|--------------|--------|
| **E1** | SQLite 每次 `execute`/`query` 都重新编译 SQL（无语句缓存） | 插入一行 20 列 **13,917 ns**；查询一行 **16,020 ns** | **所有 SQLite 读写**（本项目 4 个 Rust 消费方都用 SQLite） |
| **E2** | 连接池单一 `Mutex<VecDeque>` + 3 个全局原子计数 | 单线程 147 ns → **8 线程 650 ns（4.4× 劣化）** | 高并发下每线程都在抢同一把锁（**百万设备场景的直接瓶颈**） |
| **E3** | 宽表按列名取值每次都 `to_ascii_lowercase()`（分配 String） | 20 列查 20 次 **55.7 ns/次，每次 1 次堆分配** | 每装载一行 = N 次小分配 |
| **E4** | 读会话获取克隆整个副本列表 `Vec`，且每次过策略 `RwLock` + 小写化 | **209.6 ns / 2 次分配** | 每次只读查询 |

### 12.2 优化与实测结果

| 优化 | 做法 | 优化后 | 改善 |
|------|------|--------|------|
| **E1 语句缓存 + 参数借用** | `prepare_cached`（容量 64，LRU）+ 参数改 `ValueRef` 借用（Text/Blob 不复制） | 插入 **9,012 ns**、查询 **6,336 ns** | **1.54× / 2.53×** |
| **E2 连接池分片** | 空闲队列按线程分片（CPU 核数 2–16 片，线程本地缓存偏好分片）、统计计数按分片独立 | 8 线程 **194.2 ns** | **3.35×**（劣化 4.4× → **1.28×**） |
| **E3 列名索引双键 + 共享惰性** | 索引同时含原文键与小写键（原文命中零分配）；索引由整个结果集共享，**首次按名取值才构建** | **17.1 / 16.1 ns，零分配** | **3.3×，分配 200 万 → 0** |
| **E4 读会话快路径** | 副本列表改 `Arc` 快照；`has_replicas` / `rw_needs_check` 原子短路（无副本、无忽略表时零锁零分配） | **166.6 ns / 1 次分配** | 1.26×，分配 -50% |
| **E5 批量写入投影** | 列→行内位置按首行算一次（原来每行每列线性比较列名，20 列 × 5000 行 = 200 万次） | 批量 **9,492 ns/行**（分配 106 → 86） | 1.17× |
| **E6 写入缓存失效快路** | `has_caches` 原子标志：从未创建任何缓存时 `invalidate_cache` 直接返回 | 写路径 4 次锁 + 1 次分配 → **0** | 写多读少场景免全量开销 |

### 12.3 优化前后完整对照（本机 release，`--test-threads=1`）

```
                                    优化前              优化后
会话借出+归还（单线程）              147.3 ns            151.8 ns      持平
会话借出+归还（8 线程并发）          650.4 ns            194.2 ns      3.35×
读会话获取（read_session_for）       209.6 ns / 2 分配    166.6 ns / 1 分配
行取值 20 列（原文列名）              55.7 ns / 有分配     17.1 ns / 0 分配   3.3×
行取值 20 列（小写列名）              55.9 ns / 有分配     16.1 ns / 0 分配   3.5×
插入一行 20 列（事务内）           13,917 ns / 146      9,012 ns / 126    1.54×
批量插入摊销（5000/批）              11,139 ns / 106      9,492 ns / 86     1.17×
查询一行 20 列                    16,020 ns / 76       6,336 ns / 56     2.53×
模型表查找（176 表）                 15.2 ns             16.0 ns          持平
脏登记 / 脏周期 / 缓存元数据          35.9 / 132.6 / 13.5 ns（不变，均零分配）
```

**内存**：`DbRow` **40 字节**（列名索引改成共享 `Arc` 指针后比原先内联 `OnceLock` 更小）；
池分片结构约 +1KB/池；语句缓存 ≤64 条/连接（每条编译后语句几 KB 级，按 SQL 文本淘汰）。

### 12.4 结论：对百万级设备高并发的支撑面

| 维度 | 结论 |
|------|------|
| **CPU** | 读路径（会话获取 + 行取值）从 ~265 ns 降到 ~184 ns 且**零堆分配**；写路径框架开销占比降到 15% 以内（其余是 SQLite 执行） |
| **线程** | **仍然零新增线程**（池分片、语句缓存都在调用方线程内完成） |
| **锁** | 高并发争用点从「1 把全局池锁」变为「每线程 1 个分片锁」→ 8 线程吞吐劣化 4.4× → **1.28×**，可线性扩展到核数 |
| **每连接额外内存** | 语句缓存 64 条 × 数 KB ≈ 百 KB 级/连接；连接池上限仍默认 1000，可按业务调小 |
| **分配** | 读路径零分配；写路径每行分配 = 列数 × 4 左右（列名 + 值 clone，属实体 API 的固有成本） |

**百万设备并发的关键不在 ORM 本身**，而在业务架构（每条消息短事务、实体即用即弃、批量写优先）。
ORM 侧现在满足两条硬指标：
1. **热路径不分配**（读）→ 无 GC 压力、无内存碎片；
2. **并发不争用**（池分片）→ 线程数增加时吞吐线性上升。

### 12.5 剩余的优化空间（已评估，暂不做）

| 候选 | 预估收益 | 不做的原因 |
|------|---------|-----------|
| `SqlSession::execute` 增加借用参数重载（批量路径免每行 20 次值 clone） | 批量插入再快 ~5% | 需为 16 个驱动各实现一遍，收益小于改动风险 |
| `prepare` 的每行列名 `String` 改 `Cow<'static, str>` | 每行省 ~20 次小分配（~15%） | 需改公开拦截器 trait 签名，破坏自定义拦截器 |
| `DbValue::Text(String)` → `Arc<str>` | 大文本（JSON/报文）装载与缓存复用 | 破坏公开值类型 API，消费方全改 |
| MySQL/PostgreSQL 驱动的语句缓存对齐 | 非 SQLite 消费方受益 | 当前 4 个 Rust 消费方都用 SQLite；等有 MySQL 消费方再做 |
| SQL 字符串拼接合并（少 2 次大 `String` 复制） | 每行 ~200 ns（2%） | 收益过小 |

> 维护纪律（追加）：改动 `sqlite.rs`（语句缓存/参数绑定）、`pool.rs`（分片）、
> `session.rs`（列名索引）、`cache.rs`（`has_caches` 快路）后，必须重跑本报告 12.3 的基准并对比。

## 十三、第十二轮：其它驱动对齐 / 池开销拆解 / DH.NCode 再盘点

### 13.1 各数据库驱动能力对齐（回答「其它数据库是否也有前面的支持」）

| 能力 | SQLite | MySQL | PostgreSQL | SQL Server | Oracle | ODBC/HANA/ClickHouse |
|------|--------|-------|-----------|-----------|--------|---------------------|
| **语句缓存**（免重复编译） | ✅ 本轮加（`prepare_cached`，容量 64） | ✅ crate 内建，本轮把 `stmt_cache_size` 调到 **64** | ❌ 每次 Parse+Bind（见 13.4） | ❌ | ❌ | N/A（内联字面量） |
| **参数借用**（Text/Blob 不复制） | ✅ 本轮（`ValueRef`） | ❌ crate 要求 owned `Value` | ✅ 本轮（`PgParam<'a>` + 直接写字节） | ✅ 本轮（`MssqlParam<'a>`） | ❌（`Box<dyn ToSql>` 接口限制） | N/A |
| 参数化绑定 | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ 内联字面量 |
| 读写分离（`read_session`） | ✅ 与驱动无关 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 批量写入（多行 VALUES） | ✅ | ✅ | ✅ | ✅ | 逐条回退 | 逐条回退 |
| 结构迁移/反向工程 | ✅ | ✅ | ✅ | ✅ | ✅ | 部分 |

**本轮实际改动**：
1. **PostgreSQL**：`params.iter().cloned()` → 借用（省每列 1 次 `DbValue` 克隆）；
   `to_sql` 里 `Text` 直接 `extend_from_slice(v.as_bytes())`（省每列 1 次 `String` 复制）。
   → 单行 20 列文本插入**少 40 次堆分配**。
2. **SQL Server**：`MssqlParam<'a>(&'a DbValue)`，去掉参数克隆（`Cow::Borrowed` 本来就有）。
3. **MySQL**：`stmt_cache_size(64)`（原来用 crate 缺省值，同构 SQL 编译次数更多）。
4. **Oracle**：保留现状（`oracle` crate 的 `ToSql` 要求 `Box<dyn ToSql>`，借用化需改 crate 接口约定，
   收益与风险不匹配；Oracle 消费方目前为零）。

### 13.2 连接池开销拆解（回答「池开销能否省掉」）

新增 `tests/pool_bench.rs` 把 152 ns 拆开（本机 release）：

```
池骨架（Mutex + VecDeque 取/放）        22.6 ns   ← 硬成本，去掉池就变成「每次建连接」（100 µs 级）
Instant::now ×2（判过期 + 记时刻）     118.4 ns   ← 占 78%，**可换成系统粗时钟**
Box::new + drop（会话包装）             0.0 ns   ← LLVM 优化掉，无需处理
thread_local 读+写 ×2                   0.0 ns   ← 说明「线程本地缓存」方案换不来收益
原子计数 ×2（复用/创建统计）             9.6 ns
```

**已做**：把两次 `Instant::now()` 换成 `coarse_now_ms()`
（Windows `GetTickCount64` ≈0.7 ns；Unix 进程内 epoch + `Instant::elapsed`），
空闲超时用**毫秒精度**判定（30 秒超时完全够）。

| 基准 | 优化前 | 优化后 |
|------|--------|--------|
| 会话借出+归还（单线程） | 151.8 ns | **90~93 ns（1.66×）** |
| 读会话获取（`read_session_for`） | 166.6 ns | **96.4 ns（1.73×）** |
| 会话借出+归还（8 线程） | 194~247 ns | 207~281 ns（**噪声区间重叠**，8 线程本身波动 ±25%） |

**要不要「省掉池」？逐项判断**：
- **不能省**：省掉池就是每次操作新建数据库连接（SQLite 文件打开 + PRAGMA ≈ 100 µs，MySQL/PG 握手 / TLS 更贵），
  比池开销贵 **1000 倍**以上。
- **Mutex 22 ns 不值得再优化**：改「线程本地会话缓存」最多省 22 ns（thread_local 实测 0 ns 说明访存不是瓶颈），
  却要处理「线程退出时归还/关闭」「会话分布不均」「Dal 多实例 key」等复杂度，风险远大于收益。
- **结论**：池开销已从 152 ns 降到 ~91 ns，剩余部分 ≈ 一次 `Mutex` + 一次队列出入，
  相对一次 SQL 往返（6~9 µs）占 **1.3%**，**已到合理下限**。

### 13.3 DH.NCode 再盘点（回答「还有什么要迁移」）

对照 `DH.NCode` 全部 `.cs` 文件逐目录核对，**本轮补上唯一还缺的高价值能力**：

| C# 能力 | 本轮状态 |
|---------|---------|
| **`Entity/IEntityAddition.cs` + `AdditionalFields`（原子累加）** | ✅ **本轮实现**：`TableRef::increment` / `increment_by_pk` / `Entity::increment` + `increment_sql_owned_named`（`SET c = c + ?`）；IoT 计数/流量场景刚需（并发不丢更新） |
| `Statistics/*`（统计表 + `StatHelper.GetOrAdd`） | ✅ **等能力**（`increment` + `upsert_by_key` 组合即可；`GetOrAdd` 的插入-冲突-重查逻辑在 `upsert_by_key` 内） |
| `Common/ValidHelper.cs`（`Object`→强类型批量转换） | 有意不做（Rust 强类型 + `DbValue::as_*`，无装箱场景） |
| `Common/KeyedLocker.cs`（8 桶键锁） | 有意不做（单机由业务用 `Mutex`/分片锁；跨进程去重属应用层） |
| `Code/SearchBuilder.cs`（UI 搜索→Where） | 有意不做（`Where` 组合足够） |
| `DataAccessLayer/WindowFunction.cs` | 有意不做（需要时手写 SQL 片段） |
| `Linq/*`、`Transform/*`、`HtmlBuilder`、`DbCache`、`Fields`、`LongCount` | 有意不做（前表已列明理由） |
| `Membership/*`（用户/角色/菜单/部门/地区/租户） | 有意不做（.NET 特定接口；Rust 侧用 `Pek.RAdmin` 或各项目自研） |

> 结论：**DH.NCode 的业务能力已基本对齐**；剩余项均为「.NET 生态特有」或「Rust 有更直接替代」，
> 不是能力缺口。后续如需支持某个具体场景，按需补即可。

### 13.4 已知未做（1 项，仅影响 PG/MSSQL/Oracle 高并发写）

**PostgreSQL / SQL Server / Oracle 的语句缓存**：三个 crate 的 API 都是
`client.execute(sql, params)`（每次 Parse+Bind，语句不可复用），要缓存需自行维护
`HashMap<String, Statement>` 并对每条 SQL 做 prepared-statement 复用。
- 收益：同构 SQL 免重复解析（PG 解析占单语句 20~40%）；
- 风险：三条驱动各一套缓存实现 + 无真实数据库可验证（当前 4 个 Rust 消费方都用 SQLite）；
- 结论：**列入待办，等有真实 PG/MSSQL 消费方时再实施**（不建议在无法端到端验证的情况下动驱动核心）。

## 十五、客户端侧 MySQL 优化（服务端 `my.cnf` 不可改）

### 15.1 约束

用户明确：**「my.cnf这种目前来说没法改先不考虑这个方案」**（托管/运维冻结环境）。
→ 服务端参数（`innodb_flush_log_at_trx_commit`、`max_connections`、`innodb_buffer_pool_size` 等）
一律**不作为方案**；只在文档中标为「能改时可选」。

### 15.2 客户端侧能做的全部（已实现）

| 手段 | 实现位置 | 效果 |
|------|----------|------|
| **连接池预热** | `Pool::prewarm(count)` / `Dal::warmup_pool(count)` | 首次写入不再逐条建连（MySQL 建连含握手+认证 ≈ 3~4 次往返） |
| **`PoolMinSize=` 连接串触发自动预热** | `Dal::pool_options_from` | 打开即预热，业务代码零改动 |
| **`PoolIdleTime=`（秒）** | 同上 | 低频 IoT 默认 30s 太短；建议 300s 复用连接 |
| **`PoolMaxSize=`** | 同上 | 防打满 `max_connections`（服务端不可调时更关键） |
| **`StatementCacheSize=`** | `mysql.rs`（默认 256） | 命中即省一次 prepare 往返 |
| **`InitCommand=`** | `mysql.rs` | **会话级**参数（`SET SESSION innodb_lock_wait_timeout`、`sql_mode`、隔离级别）——没有 `my.cnf` 权限也能调 |
| **批量 + 大事务** | `insert_batch`/`upsert_batch`/`EntityQueue`/`save_batch` | 把 COMMIT 的 fsync（≈570 µs）摊到每批，**唯一的大杠杆** |
| **`SslMode=None`**（内网） | `mysql.rs` | 省 TLS 握手与加解密 |
| **参考实现** | `examples/iot_telemetry.rs` | 可直接照抄的生产模板 |

### 15.3 关键设计取舍：预热默认关闭

`PoolOptions::min` 默认是 CPU 核数（2–8），**不能**拿它当预热信号 ——
试过「min>0 即预热」，结果 lib 测试 `dal_pool_reuses_sqlite_session_and_can_be_disabled`
在池化关闭时仍建了 8 个连接（语义冲突），且每个 `Dal` 打开都白建 8 条连接（SQLite 也多花 ~800 µs）。
→ **改为：「连接串显式给了 `PoolMinSize=` 才预热」，另留 `warmup_pool()` 供手动调用**。

### 15.4 实测（`examples/iot_telemetry.rs`，release，200,000 行 / 1,000 设备）

| 后端 | 吞吐 | 说明 |
|------|-----:|------|
| SQLite（本地文件） | **417,948 行/秒** | 0.48 s 完成 |
| **MySQL（MariaDB 11.8.9 回环，`PoolMinSize=4` 预热）** | **143,677 ~ 183,521 行/秒** | 1.09~1.39 s；预热 4 连接生效 |

写法：`EntityQueue` + `upsert_tracked_static`（行内含主键 → 多行 Upsert 快速路径）
+ `set_batch_size(500)` + 200 ms 时间闸门 flush + 关闭前最终 flush。

> 对比逐条 `save()`（1,477 行/秒，见 §14）：**批量后 ≈ 100~125 倍**。
> 这正是「服务端不能改」时的答案——**不是让数据库更快，而是让每次往返装载更多行**。

### 15.5 客户端无法消除的部分

1. **一次 COMMIT 的 fsync**（≈570 µs，本地 SSD；机械盘/云盘更高）：
   只能靠批量摊薄（500 行/批 → 1.1 µs/行），不能清除。
2. **乐观/悲观锁竞争、缓冲池命中率、临时表落盘**：纯服务端行为。
3. **网络 RTT**：跨机房时批量更关键（同批量下吞吐 ≈ 1/RTT）。

## 十六、SQLite 与 MySQL 的同条件对比 + 一个统计口径 Bug

### 16.1 触发

用户提问：**「mysql就是会比sqlite性能低很多么？」**
—— 上半轮给出的「SQLite 41.8 万行/秒 vs MySQL 14.4 万行/秒（2.9×）」需要拆开看是否公平。

### 16.2 先发现一个真 Bug：MySQL Upsert 的统计翻倍

重跑基线时 MySQL 报出 **40 万行**（实际 20 万），SQLite 报 20 万 —— 定位到
`EntityQueue::flush` 把 `write_batch_rows_core` 的返回值（驱动 affected_rows）直接累加：

- MySQL 的 `INSERT ... ON DUPLICATE KEY UPDATE` 对**插入行返回 1、更新行返回 2**；
- SQLite/PG 的 `ON CONFLICT DO UPDATE` 返回 1。

→ 重复上报（全是更新）时 MySQL 的统计正好翻倍。**只影响统计，不影响数据**。
修复：
1. `Dal::write_batch_rows_core` 在 `Upsert + DatabaseKind::MySql` 时把 affected 归一化为**逻辑行数**
   （`affected > 0` → 本批行数，全无变化 → 0），`save_batch` / `upsert_batch` 一并受益；
2. `EntityQueue::flush` 的 Upsert 段直接按 `run.len()` 计；
3. `tests/mysql_e2e.rs` 新增回归：4 行全更新时返回值必须是 4（不是 8）。

### 16.3 公平对比（同代码、同数据量 20 万行、批 500）

| 后端配置 | 吞吐 | 每次提交 fsync |
|----------|-----:|:--------------:|
| SQLite WAL + `Synchronous=Off`（默认，对齐 C#） | **41.2 万行/s** | ❌ |
| SQLite WAL + `Synchronous=Normal` | 40.3 万行/s | ❌ |
| SQLite WAL + `Synchronous=Full` | **26.9 万行/s** | ✅ |
| MySQL `flush_log_at_trx_commit=0` | 17.4 万行/s | ⏱ 每秒 |
| MySQL `flush_log_at_trx_commit=1`（默认） | **14.2 万行/s** | ✅ |
| MySQL 纯新增 / 全更新（清表 vs 不清表） | 14.2 万 / 14.3 万 | ✅（几乎无差） |

### 16.4 归因

- **默认配置的 2.9× 不是同一条线**：SQLite 默认 `Synchronous=Off` 不等落盘（主机断电可丢提交），
  MySQL 默认每次提交 fsync。真正的同等级对比是 **26.9 万 vs 14.2 万 = 1.9×**。
- MySQL 侧 fsync 只占 ~22%（14.2→17.4 万）→ **引擎处理（聚簇索引 + undo/redo record + 完整 SQL 解析）是主成本**；
  SQLite 侧 fsync 占 ~35%（41.2→26.9 万），因为它只有这一层保护。
- **网络不是主要成本**：回环往返 92 µs × 400 批 ≈ 37 ms = 1.40 s 的 2.6%。
- 绝对量级：14.2 万行/s ≈ **每天 123 亿行**；SQLite 的高吞吐以「单进程单写者、同机、无主从」为前提，
  多实例并发写或需要在线备份时不可用 —— **比的不是快慢，而是能不能**。

### 16.5 顺带

`examples/iot_telemetry.rs` 新增 `RCODE_IOT_CONN`（显式连接串，优先级高于 `RCODE_MYSQL`），
便于用同一程序对比不同 `Synchronous=` / 后端配置。

## 十七、框架侧剩余空间归因 + 修掉一条慢 125 倍的路径

### 17.1 分层归因（新工具 `examples/iot_attrib.rs`）

一批 500 行 Upsert 的 3138 µs 拆开（MariaDB 回环；**值每轮变化**，否则 MySQL 判定
「设为当前值」直接跳过写入，测出来是假快）：

| 环节 | 每批 | 占比 |
|------|-----:|-----:|
| SQL 拼接（7200 字节 / 2000 占位符） | 6.2 µs | **0.2%** |
| 参数构造 + 分配（2000 个值） | 91.1 µs | **2.9%** |
| 网络往返（回环 98 µs/次） | 98.0 µs | **3.1%** |
| **服务端 InnoDB** | **2942.6 µs** | **93.8%** |

→ **客户端（拼接 + 参数）合计 3.1%，已到地板**；93.8% 在服务端，而 `my.cnf` 拿不到，
只能靠「少写行 / 少写列 / 少建索引 / 批次覆盖更多行」从业务侧减负。

上层（`EntityQueue` + 通道）比裸路径再慢约 9%（0.65 µs/行），分散在「每行一次 `Vec` 分配 +
通道投递」上；再抠需要重构队列数据结构，**评估后不做**。
「flush 后复用 `self.items` 容量」能省约 0.5% CPU，但会让每个队列实例常驻约 40 KB ——
与「减少资源消耗」的目标相反，**不做**。

### 17.2 真问题：脏列 Upsert 退化成逐条（125 倍）

`enqueue_save`（生成实体的默认形态）对已存在行走 `upsert_tracked(..., Some(脏列))`；
而队列的多行 Upsert 快速路径原条件是「**所有行 `update_columns` 都为 `None`**」——
只要带脏列就整体退化成逐条 `find_by_pk` + `update_by_pk`。

| 写法（1000 行，MySQL 回环） | 每行耗时 | 相对 |
|-----------------------------|---------:|-----:|
| 多行 Upsert（全列） | 6.3 µs | 1× |
| **脏列 Upsert（修复前）** | **789.6 µs** | **125×** |
| **脏列 Upsert（修复后）** | **10.5 µs** | 1.7× |

修复：
1. `sqlbuild::multi_write_sql_upsert_named(..., update_only)`：多行 Upsert 支持「指定只更新哪些列」；
2. `TableRef::write_batch_rows_upsert(rows, update_only, batch)`：对应执行入口；
3. `EntityQueue::flush` 的 Upsert 段**按更新列集合分组**（`same_column_set`：顺序无关、大小写不敏感），
   同组一条多行 Upsert；行内缺主键的仍走逐条；
4. 语义不变：**插入写全列，更新只写脏列**（回归 `tracked_upsert_batches_and_only_writes_dirty_columns`
   同时覆盖「不同脏列集合分组」与「非脏列保持原值」）。

### 17.3 结论

- 框架侧性能：**已到地板**（客户端 3.1%，且其中 2.9% 是参数无法避免的构造）。
- 本轮唯一有意义的收益来自「**消灭退化路径**」（125×），不是抠微秒。
- 后续若还要提吞吐，方向只能是业务侧：采样/聚合上报、减少列、单表少索引、提高每批行数。
