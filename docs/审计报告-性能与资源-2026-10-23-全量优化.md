# 全量审计报告：写路径优化（2026-10-23 五轮）· 性能与资源评分

> 范围：2026-10-23 全天对写路径（插入 / 更新 / CAS / 批量 / 分表批量）的性能与资源优化。
> 基线：`docs/审计报告-性能与资源-2026-10-22.md`（优化前）与本报告「首版」列。
> 命令：`cargo test --release --test perf_guard -- --ignored --nocapture --test-threads=1`
> 结论：**性能 5/5、资源占用 5/5（显著达标）**；无基准回退 >5%。

## 一、改动清单

### 1. 新增能力

| 项 | 说明 |
|----|------|
| `TableRef::update_if` / `Entity::update_if_unchanged` | 条件更新（CAS）：旧值进 `WHERE`，冲突返回 `0` / `Error::Conflict` |
| `Error::Conflict` | 并发冲突错误类型 |
| `SqliteOptions` / `SqliteSession::open_with_options` | SQLite 参数可配（`Synchronous` / `Cache Size` / `Journal Mode` / `BusyTimeout` / `Readonly`） |
| `DatabaseKind::push_quoted` / `push_placeholder` | 零分配追加式引用/占位符（与 `quote`/`placeholder` 逐字节等价，单测护栏） |
| `sqlbuild::update_by_pk_sql_owned_named` / `update_by_pk_sql_named` | 按主键 UPDATE 直接拼接（不构造 `Where`） |
| `TableRef::write_batch_rows_core` + `BatchField` / `BatchRow`（crate 内） | owned / 借用行共用批量执行核心 |
| `interceptor::has_registered` | 写入路径无锁快路（未启用拦截器时零锁零分配） |

### 2. 行为变更

- **SQLite 默认 `Synchronous=Off`**（对齐 C# DH.NCode `SQLite.cs`）+ `Journal Mode=WAL` + busy_timeout 5s；
  连接串可覆盖（键名同 C#）。断电风险由项目按需选择 `Synchronous=Normal`。
- 无拦截器 / 非分表时写路径走借用快路（语义与 owned 路径逐字节等价，`batch_e2e` 覆盖）。
- 分表批量（`write_batch_auto_sharded`）改为泛型行 + 行引用分组，**去掉每行 `row.clone()` 深拷贝**。

### 3. 删除/内部整理

- 删除 `update_if_sql_owned_named`（并入 `update_by_pk_sql_owned_named`）。
- 删除 `ShardBatchRows`（分组改为 `Vec<(&ShardModel, Vec<&Vec<F>>)>`）。
- 拦截器注册表 `Mutex<Vec<_>>` → `RwLock<Arc<Vec<_>>>` + `HAS_INTERCEPTORS` 原子快路。

## 六、风险与边界

1. **`Synchronous=Off` 默认**：断电/硬重启可能损坏数据库（C# 源码注释亦承认）。需要强一致的项目请在连接串设
   `Synchronous=Normal`（WAL 下不会损坏，掉电最多丢最近事务）。
2. **CAS 的 `expected` 列必须有索引/主键**，否则会全表扫描。
3. **分表批量**已支持借用行；**实体层 `Entity::insert_batch_sharded` 仍走 owned 行**（`BatchGroup` 未泛型化，
   每行多约 20 次分配），列为后续候选。
4. 有拦截器场景仍走 `prepare` 的 owned 转换（`EntityInterceptor` 公开签名未改，避免破坏消费方）；
   无拦截器场景已零拷贝。
5. `find_by_pk` / `delete_by_pk` 未做主键直拼（SELECT 方言分页复杂；查询 5.77 µs 中框架构建 <2%）。
6. 批量路径瓶颈已转移到 **SQLite 执行与参数绑定**（每行 20 列），继续压缩框架分配收益有限。

## 七、MySQL 专项核对（2026-10-23）

### 7.1 已自动受益（方言无关）

- SQL 拼接零分配（`push_quoted`/`push_placeholder`、`update_by_pk_sql_*`、`insert_sql_named`）；
- 无拦截器借用快路（`insert` / `update_by_pk` / `update_if`）；
- 批量执行泛型化（`BatchField` / `BatchRow`，分表批量去 clone）；
- CAS 一条语句（无额外往返、无额外索引扫描以外的开销）。

### 7.2 MySQL 专属已做

| 项 | 状态 |
|----|------|
| 预编译语句缓存 `stmt_cache_size(64)` | ✅（crate 内建，同构 SQL 只编译一次） |
| 多行 `INSERT`（5000/批，按 `max_statement_params=65535` 收紧） | ✅ |
| `tcp_nodelay` | ✅ crate 默认 `true`（不累积小包延迟） |
| 连接池（按线程分片）、TLS（native / rustls） | ✅ |
| 会话初始化 `SET NAMES` | ✅ |

### 7.3 本次修复

- **覆写 `MysqlSession::insert_and_get_identity`**：插入后直接读驱动 OK 包里的 `last_insert_id`，
  **单行插入少一次 `SELECT LAST_INSERT_ID()` 网络往返**（远程 MySQL 约 0.1~1 ms/次）。
  通用 `last_identity()` 仍保留查询语义（中间夹其它语句时更稳）。

### 7.4 驱动固有 / 未做

- 参数绑定 `Value::Bytes` 为 owned（`mysql` crate 协议要求），`Text`/`Blob` 每次执行复制一次；
  无法像 PG 的 `PgParam<'a>` 那样借用。
- 每次 `execute` 构造 `Vec<Value>`（参数个数次分配）；可复用缓冲但收益 <50 ns，暂不做。
- `stmt_cache_size` 未做成连接串可配（默认 64；多表×多列集可调大）。
- `compress` 默认关闭（小包高频场景不建议开）。

### 7.5 结论

MySQL 路径在**框架层已优化到位**；剩余成本主要是驱动协议与网络往返，本次已消除单行插入的额外往返。
真实 MySQL 基准需在具备实例的环境执行（`tests/mysql_e2e.rs` 由环境变量门控）。

## 八、按 IoT 量级重估微优化（2026-10-23 · 第十六轮）

### 8.1 触发

用户原话：

> 「你说的这些收益小的没有考虑到物联网高并发的场景还是看不起我们的设备量」

**复盘结论：判断口径错了。** 之前用「单次调用耗时占比」评价优化价值，正确口径应是
「在目标 QPS 下折算成多少 CPU 核」。换算（单实例、每次写入执行一次该操作）：

| 单次开销 | 100 万次/秒 | 1000 万次/秒 | 1 亿次/秒 |
|---------:|------------:|-------------:|----------:|
| 50 ns | 0.05 核 | 0.5 核 | 5 核 |
| 100 ns | 0.1 核 | 1 核 | 10 核 |
| 500 ns | 0.5 核 | 5 核 | 50 核 |
| 1 µs | 1 核 | 10 核 | 100 核（不现实） |

即：**任何 ≥100 ns 的固定开销，在千万级写入下都是「核」级别**，不能按「占比小」忽略。
本轮据此重查拦截器写入路径（IoAT 场景几乎必然启用 `enable_defaults()`），发现三项被低估的成本。

### 8.2 修正项

| # | 问题 | 修复 | 单次收益 |
|---|------|------|---------:|
| 1 | 有拦截器时列名全部 `to_string()`（每列一次堆分配） | 新增 **Cow 列名通道**：`EntityInterceptor::on_valid_cow`（默认转 owned，兼容自定义拦截器）+ `interceptor::prepare_static` + `TableRef::{insert_static, update_by_pk_static, update_if_static}`；`Entity::{insert_with, update_with, update_with_expected}` 全走静态列名 | 列名分配 **N → 0** |
| 2 | `chrono::Local::now()` 每次写入查一次时区（Windows 走注册表 + 锁） | `interceptor::audit_now()` **毫秒级缓存**（同一毫秒内复用；系统时间戳用 `SystemTime` 取，~20 ns） | **≈450 ns** |
| 3 | `TraceContext::current()` 每次写入抢全局 `Mutex`（无 trace 时也要抢） | 加 `AtomicBool` 快路：未设置 TraceId 时**一次原子读**返回 | **≈40~60 ns** |
| 4 | 三个内置拦截器每次写入各扫全表列判断 `on_init` | `TableMeta::audit_flags()` **审计列位图**（`OnceLock<u16>` 首次扫描缓存；`PartialEq` 手写忽略缓存字段） | ≈100 ns（宽表更多） |

### 8.3 实测（SQLite，事务内，2 万次，预热 2000 次；`bench_interceptor_write_paths`）

| 场景 | 耗时 ns/op | 分配/次 |
|------|-----------:|--------:|
| `update_by_pk`（**无**拦截器，借用快路） | 981.2 | 9 |
| `update_by_pk`（三件套，owned 列名）· 优化前 | 2513.8 | 21 |
| `update_by_pk`（三件套，owned 列名）· 现在 | 2106.7 | 21 |
| `update_by_pk_static`（三件套，Cow 列名）· **现在** | **1837.4** | **16** |
| `update_by_pk_static`（仅 Time）· 优化前 → 现在 | 2314.8 → **1756.7** | 16 → 16 |
| `insert`（三件套，owned）· 优化前 → 现在 | 5277.8 → 4630.0 | 32 → 32 |
| `insert_static`（三件套，Cow）· **现在** | **4487.4** | **24** |

结论（有拦截器的写路径，即 IoT 常态）：

- `update`：**2513.8 → 1837.4 ns（−26.9%）**，分配 **21 → 16 次（−24%）**；
- `insert`：**5277.8 → 4487.4 ns（−15.0%）**，分配 **32 → 24 次（−25%）**；
- 折算 1000 万次/秒：`update` 省 **≈6.8 核/秒**，每秒少 **5000 万次**堆分配（分配器争用同步下降）。

### 8.4 兼容性

- `EntityInterceptor` 新增 `on_valid_cow` **有默认实现**（内部转调 `on_valid`）→ 自定义拦截器无需改动；
- `TableRef::*_static` 是**新增** API（`&[(&'static str, DbValue)]`），原 owned/借用接口全部保留；
- `audit_now` 只影响审计列时间的**毫秒内一致性**（同一毫秒复用同一时间戳），与 C# `DateTime.Now`
  的时钟粒度缓存行为一致；跨毫秒仍取真实时间；
- `TableMeta::audit_flags()` 缓存不参与 `PartialEq`（同一模型初始化前后仍相等，结构比对不受影响）。

### 8.5 评估后仍不做（并说明理由）

| 项 | 为什么不做 |
|----|-----------|
| `prepare` 中的 `DbValue` 克隆（每列一次 Text 复制） | 参数需在 `execute` 期间存活；改借用需 16 个驱动签名全改，风险远大于收益（单列 ~20 ns） |
| `snapshot()` 的 `RwLock` 读 + `Arc::clone`（~20 ns/写） | 换 `ArcSwap` 需引入依赖；20 ns × 千万次 = 0.2 核，收益/风险比不佳 |
| `TableMeta::column()` 建 O(1) 列名索引 | 位图已覆盖拦截器热路径；剩余调用点（校验、取值）不在每次写入的固定开销里 |
| 批量路径的 `Vec<(&str, DbValue)>` 复用缓冲 | 批量摊销后 <20 ns/行，且 API 语义（借用调用方切片）更清晰 |

### 8.6 评分（本轮维持）

- **性能：5/5**（写路径整体再降 15~27%，且是「有拦截器」这一最常用路径）；
- **资源：5/5**（每写分配 21→16 / 32→24，堆压力与分配器争用同步下降；无线程、无新增常驻内存，
  `TableMeta` 仅 +32 字节/表）。
